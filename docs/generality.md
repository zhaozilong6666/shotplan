# 这不是一个旅拍项目

> 一句话：**一个把 LLM 放进「硬约束 + 独立校验 + 受控修复 + 可测量」闭环里的约束规划器**，
> 用旅拍做载体，因为它的约束最密、最容易验证、也最容易讲清楚。
>
> 如果你只记住一件事：**这个项目的价值不在「排出一份好看的照片行程」，
> 而在「它知道自己不知道，并且能被证明」。**

## 为什么用旅拍当载体

不是因为旅拍好做，而是因为它把 LLM 落地的三个真问题一次性暴露出来：

| 问题 | 旅拍里的表现 |
| --- | --- |
| 约束密集且互相冲突 | 6 小时里要装下妆造 90 分、2 个地点、2 段转场、黄金光线窗口、预算上限 |
| 答案可对可错 | 「16:00 到故宫」是硬错（16:00 停止入馆），不是风格问题 |
| 用户会提做不到的需求 | 预算 400 元 + 8 小时 + 两个收费景点，物理上不可行 |

换成排班、排课、手术排期、展会日程、物流调度，这三条一模一样。
真正需要替换的只有「领域知识」和「规则阈值」，不是引擎。

## 通用内核 vs 领域外壳（有数据）

2026-11-16 实测的领域词耦合度：

| 模块 | 行数 | `妆造/汉服/拍摄/shoot/makeup` 出现次数 | 判断 |
| --- | ---: | ---: | --- |
| `pipeline.py` 编排、预算、修复循环、错误边界 | 655 | **6** | 通用 |
| `tracing.py` 可观测性 | — | **0** | 通用 |
| `storage.py` 持久化 | — | **1** | 通用 |
| `agents/openai_compatible.py` provider | — | 0 | 通用 |
| `domain/constraints.py` 15 条规则 | 220 | 26 | **领域适配** |
| `agents/validator.py` 校验器 | 355 | 32 | **领域适配** |

也就是说：**约 1000 行是「任何约束规划域都能用」的骨架，约 575 行是需要重写的领域层。**

规则的划分不靠感觉，靠 `python -m evals.domain_portability` 实测：

```
16 rules
  wording without domain words : 5/16 = 31%
  logic reusable in another domain: 15/16 = 94%
-> STYLE_MISMATCH (soft) logic=domain-specific
```

两个口径差这么多，恰好说明了问题所在：**规则逻辑本身几乎都是通用的，领域词是「文案污染」**。
换句话说，换领域的工作量主要在改名和改数据，不在重写推理。

## 换一个领域要改什么（精确清单）

假设换成「会议室排期」：

| 要改 | 具体内容 | 规模 |
| --- | --- | --- |
| 知识库 schema | `locations.json` → `rooms.json`（容量、设备、楼层、可预约时段） | 1 个文件 |
| 规则表 | 15 条里 **14 条逻辑可迁移**（`python -m evals.domain_portability` 实测）：按关键词扫描 **11 条文案含领域词**（「拍摄」→「会议」）、4 条文案也完全通用；1 条真正领域特有（`STYLE_MISMATCH`：风格与场景的匹配）。**文案层面只有 4/15 完全不含领域词**——这正是要改的部分 | `constraints.py` 约 80 行 |
| 校验器 | 规则文案与 `activity` 枚举（`makeup/shoot` → `setup/meeting`） | `validator.py` 约 60 行 |
| prompt | 系统提示词换域，输出 schema 不变 | `prompts.py` 1 段 |
| 离线规划器 | `mock.py` 的选点启发式 | 1 个文件 |

**零改动复用**：`pipeline.py`（编排、墙钟预算、解析信任边界、修复循环单调性）、
`evals/`（80 例回归 + 挖掘器 + 变异测试 + HTTP 压测 + 归因分析）、`tracing.py`、
`storage.py`、API、前端、30 道 CI 门禁。

换句话说：**换领域是「换数据和阈值」，不是「重写系统」。**

## 真正可迁移的是这套方法论

这半天做的所有改进，没有一条是旅拍特有的：

| 做的事 | 领域无关的原因 |
| --- | --- |
| 把光线排程从 prompt 移进代码（`LIGHT_MISUSE` 31→0） | 只要某类判断有确定算法，就不该让模型猜 |
| 拍摄块门槛随预约时长缩放（`SHOOT_TOO_SHORT` 4→2） | 「写死阈值」在任何领域都会在边界用例上误报 |
| 预算从 60s 提到 180s 再回到 120s | 预算是「覆盖 P99」而不是「拍个整数」 |
| 报告按 rules 表分级，而不是渲染处猜 | 真相必须单点定义 |
| 从 88.4% 里剥出「超时」而不是算成模型失败 | 归因错误会导错优化方向 |
| 反例用虚构 id 而不是真实城市 | 负向测试的前提不能随产品演进消失 |
| 盲测写完后才修规则，并承认它不再是盲测 | 评测的有效性依赖「先写题再改代码」 |

这些放在任何 LLM 应用里都成立，也是这个仓库最值得看的部分。

## 它明确不做什么（避免过度承诺）

- **不是通用 Agent 框架**：没有工具编排、没有多轮对话状态机、没有 RAG 检索层。
  它只做一件事：给定结构化约束，产出一个可被机器判定对错的方案。
- **不是「让模型变聪明」**：实测显示模型在光线这类领域约束上还不如规则规划器
  （`LIGHT_MISUSE` 31 次 vs 0 次），所以做法是把这类判断从模型手里拿走。
- **不是产品**：没有预约、支付、商家档期。它停在「可执行的方案」这一步。

## 如果要继续往「大」做，优先级

1. **证明可迁移**：用同一套 `pipeline + validator + evals` 跑通第二个领域（哪怕只是排期 demo），
   把「约 1000 行通用 / 约 575 行领域」从估算变成实测。
2. **补领域数据的时间维度**：`open_time` / `closed_days` 现在只在 `notes` 里，规划器读不到——
   这是真实可用性缺陷，不是分数问题。
3. **单域深挖**：真实商家、真实档期、真实报价。这是别人抄不走的部分。
