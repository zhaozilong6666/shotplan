# ADR 0008 · 模糊测试与性能基准进门禁

- 状态：已采纳
- 日期：2026-11-12
- 相关：[0001 核心零依赖](0001-core-zero-dependency.md)、[0002 校验器不经过模型](0002-validator-outside-model.md)、[0007 生成前可行性判定](0007-feasibility-before-generation.md)

## 背景

评测集证明的是「规划器在真实 brief 上足够好」。它有两个结构性盲区：

1. **输入分布之外**：用例都是人工写的、类型正确的 brief。请求实际从 JSON 进入领域模型，中间没有 schema 层（ADR 0001），所以 `hours="abc"`、`budget_cny=None`、`styles` 传字典、`NaN`、`1e400` 都能到达 `PlanRequest`。这类输入此前会抛 `TypeError`，在 API 层表现为 500。
2. **非功能性回归**：没有任何测试会因为「每次调用重新加载知识库」或「某个循环退化成 O(n²)」而失败。功能测试全绿，性能可能已经掉了一个数量级。

## 决策

把两个问题各交给一层专门的、可在 CI 里判定的检查：

**模糊测试**（`evals/fuzz.py`）

- 从真实 brief 变异生成输入，而不是随机造字符串——真实 brief 的字段组合才是最难处理的部分。
- 不变量只有一条，但绝对：`run_plan` 对任意输入返回结构化结果（`ok` / `infeasible` / `error`），绝不抛异常，结果必须可 JSON 序列化。
- 每个用例带独立种子，失败可用 `--only-seed` 单条复现；种子由**迭代序号**推导，不能由「已收集数量」推导，否则跳过的用例会让后续种子漂移。
- 门禁只判「崩溃 / 不可序列化」，不判「可行输入是否硬通过」——后者是质量问题，属于评测集，把两者混在一起会让门禁语义变模糊。

**性能基准**（`evals/benchmark.py`）

- 测量 p50/p95/p99、吞吐、Python 堆峰值与分步耗时。
- 延迟与内存**分两轮**：`tracemalloc` 会给每次分配挂钩子，混在一起会把内存开销算成延迟（实测 p50 从 0.2ms 涨到 2.6ms，虚高一个数量级）。
- 内存用 `tracemalloc` 而不是 RSS：RSS 取决于解释器、OS 和机器上其他进程，跨 runner 不可比。
- 门禁用**绝对上限**且比实测宽一个数量级（p95 < 50ms、吞吐 > 50/s、堆 < 64MB）。目的是抓数量级回归，不是卡 CI 抖动。

**配套的语义修正**

- `PlanRequest.normalized()` 改为全域函数：非法数值退化为文档化默认值并夹紧区间，非有限浮点数视为垃圾而不是「很大」。
- 非法日期在预检阶段结构化拒绝（`DATE_INVALID`），而不是让 `light_window` 抛 `KnowledgeError`。
- provider 抛错或输出不可解析时返回 `status="error"` + `PIPELINE_ERROR`，不再让异常穿透成 500。

## 后果

- 好：malformed brief 从「500」变成「结构化答案」；接口契约可以写成「任意 JSON 都有响应」。
- 好：「不崩」和「不慢」都能被 CI 判定，不再依赖人工 review。
- 代价：CI 多两个步骤（各约 1 秒）；性能门禁的数字必须随硬件升级重新校准，所以阈值写在 CLI 参数里而不是硬编码。
- 代价：展示页不能直接消费实时基准结果——时间数字跨机器不可复现，放进「展示页一致性」门禁只会造成假失败。因此页面读仓库内提交的快照 `evals/benchmark.json`，由 `make showcase` 刷新，并在 `docs/benchmark.md` 里写明这一点。

## 后续：真实 HTTP 压测沿用同一原则

`evals/http_load.py` 启动真正的 `uvicorn`（1 / 2 / 4 worker）测端到端 QPS 与多进程写 SQLite。它的门禁**只断言机器无关的契约**（0 错误、0 丢写、P95 不超过 3000ms 的宽松防挂上限），吞吐、延迟绝对值与 worker 加速比全部只进 `docs/http-load.md`。

原因与扩展性门禁那次修复一致：这些数字随 CPU、磁盘、CI 负载与样本量剧烈波动，同一台机器两次运行 4 worker 的吞吐就能从 228/s 掉到 130/s。展示页读的是已提交快照 `evals/http_load.json`，而不是实时结果——与这里对 `evals/benchmark.json` 的处理一致。
同理，成本模拟报告与展示页的 P50/P95 直接显示**价格卡配置值**：实测值会叠加本机流水线开销，
`round(1200.6)` 就会从 1200 变成 1201，让「展示页一致性」门禁偶发失败。实测值仍保留在
`evals/out/cost-latency.json` 验证聚合链路，但绝不进入被提交、被比对的产物。

## 备选方案与拒绝理由

- **用 Hypothesis 做属性测试**：能力更强，但会给核心仓库引入测试依赖，与「零依赖可运行」的取向冲突；当前变异策略已能覆盖真实的类型破坏面。若将来需要收缩/组合性质，再评估。
- **用 pytest-benchmark 做基准**：输出更专业，但会引入插件依赖，且默认统计方式不区分测量开销来源。自己 60 行实现更容易解释「为什么分两轮」。
- **把性能数据实时写进展示页**：会在 CI 一致性检查里产生必然的假失败（见上）。
- **门禁只报警不失败**：报警会被忽略。既然不变量是绝对的，就应当失败。
