# ADR 0007 · 可行性判定在生成之前，且不经过模型

- 状态：已接受
- 日期：2026-11-12
- 关联：[ADR 0002](0002-validator-outside-model.md)（校验器不经过模型）

## 背景

有一类 brief 在数学上就不可能满足：预算低于最低可执行成本、预约时长短于「妆造 → 转场 → 拍摄」最短闭环、城市不在知识库、`must_include` 与 `avoid` 互相矛盾。旧实现会照样让模型生成一份方案，然后由校验器判 `BUDGET_EXCEEDED` 或直接抛 `KnowledgeError`。两种结果都不好：前者浪费一次生成并给出误导性行程，后者把业务上正常的「需求不可满足」变成异常。

阶段 4 的评测集扩充到 36 个用例后，这个缺口被显式暴露出来：6 个用例专门描述不可满足的 brief。

## 决策

1. 在 `domain/feasibility.py` 用纯 Python 做**生成前**的可行性判定，输入只有 brief 与知识库，不调用任何模型。
2. 判定时返回结构化 `FeasibilityReport`：是否可行、逐条原因（`code` / `message` / `shortfall` / `suggestion`）以及理论下限（最低预算、最短时长、支持城市）。
3. 不可行时 `run_plan()` 直接返回 `status="infeasible"`：空方案、`INFEASIBLE` 硬问题、trace 只含 `preflight` 事件，并照常写入 SQLite。**不调用 provider、不进入修复循环**。
4. CLI 用独立退出码 `3`（区别于 `0` 成功 / `2` 校验不通过），并以「原因 + 缺口 + 建议 + 最低要求」的格式输出；API/JSON 带 `status` 与 `feasibility` 字段；Web 界面渲染专门的不可行视图。
5. 评测上把「正确拒绝」计为通过（1.0 分），把「硬凑方案」计为失败（0.0 分）。这条规则写在 `evals/scorers.py::evaluate_case`。

## 理由

- 「能不能做」和「做得好不好」是两类判断：前者是约束可满足性，可以精确计算；后者才需要生成与评分。把前者交给模型，等于让一个不擅长算术的组件去回答一个纯算术问题。
- 提前终止省掉无意义的生成与修复，对真实模型还省 token 和延迟。
- 返回结构化原因比抛异常更接近产品行为：用户可以据此改预算/时长，而不是看到一句报错。
- 与 ADR 0002 形成一致的叙事：这个系统里有两个明确「不交给 AI」的判断点，都在生成链路之外。

## 后果

- 正向：不可满足需求不再产生误导性方案；CLI/API/Web 三端行为一致；6 个专用评测用例持续守护该行为。
- 负向：可行性下限依赖静态知识库（最低妆造 300 元 + 最低场地 0 元 + 转场 50 元 = 350 元，最短 1.5 小时）。若知识库价格变化，下限自动重算，但仍是理论值而非真实商家报价。
- 负向：由于 preflight 在生成之前且不确定于 provider，`good` 与 `naive` 在这 6 个用例上共享同一结论；两组之间的区分度由其余 30 个用例提供。这一点在评测报告里如实写明。
- 缓解：为可行性判定写 9 个单元测试，含「provider 绝不被调用」与边界值（恰好 350 元 / 1.5 小时仍可行）。

## 备选方案

让模型自己判断并输出 `INFEASIBLE`（会漂移、不可单测）；只做输入校验并抛异常（丢失原因与建议，调用方难以恢复）；干脆把这类用例排除出评测集（掩盖真实缺口，拒绝）。
