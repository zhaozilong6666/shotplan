# ADR 0012 · 运行历史改为写后置队列，并给出可测量的持久性边界

- 状态：已采纳
- 日期：2026-11-13
- 相关：[0011 对照实验优先于归因推断](0011-controlled-experiment-over-inference.md)、[0008 模糊测试与性能基准不进一致性门禁](0008-fuzz-and-benchmark-gates.md)

## 背景

[worker-bottleneck.md](../worker-bottleneck.md)（v0.9.0）用开/关对照实验确认：**同步写运行历史是请求关键路径上最大的单项开销**，并留下一条建议——「把写入异步化 / 批量化，而不是删掉历史」。建议当时没有实现，也没有被验证。

同时这条建议本身有一个没回答的问题：异步写**会不会丢数据**？项目在 `docs/loadtest.md` 里对外承诺过「600 次请求 0 丢写」，如果默认改成异步，这个承诺就变成了一句未经限定的空话。

## 决策

### 1. 三种模式，默认仍是 `sync`

`Settings.persist_mode`（`SHOTPLAN_PERSIST_MODE`）取 `off | sync | async`。

| 模式 | 行为 | 默认 |
| --- | --- | --- |
| `off` | `run_plan(store=None)`，完全不写 | 否 |
| `sync` | 响应返回前提交，v0.9.0 的行为 | **是** |
| `async` | 交给进程内写线程，批量提交，退出时排空 | 否 |

默认不改，是因为「每个被接受的请求都已落库」是既有对外承诺，也是所有并发门禁的断言基础。把一个可测量的性能收益换成一个未限定的持久性弱化，然后继续沿用原来的宣传口径，是这轮改动里最容易犯的错。

`async` 作为可选模式提供，收益与代价都写清楚，由部署方选。v0.9.0 的布尔开关 `SHOTPLAN_PERSIST_RUNS=0` 继续有效（映射到 `off`），不破坏脚本与文档。

### 2. 一个进程一个写线程，不是一个请求一个

`RunWriter`（`storage.py`）持有有界队列、后台线程和一批统计。理由不是「线程池更快」，而是 SQLite 只有一个写者：让 N 个请求线程各自去抢写锁，不如让它们把行交给一个线程，由它在一个事务里 `executemany` 提交。批量把 N 次 fsync 压成 1 次。

三条硬约束：

- **不丢行**：队列满时退化为同步写（`sync_fallbacks` 计数），而不是丢弃或阻塞到超时；
- **不静默失败**：批次失败重试一次，仍失败则计入 `failed` 并继续服务，不杀掉线程；
- **可观测**：`/api/config` 在 `async` 模式下暴露 `submitted / written / pending / batches / max_batch / sync_fallbacks`。

### 3. 把「什么时候算写成功」写成一个可调用的屏障

`flush(timeout)` 阻塞到 `pending == 0`。没有这个屏障，「异步」和「丢了但没人知道」在测试里无法区分。FastAPI `lifespan` 在 shutdown 时调用 `close()`，所以 SIGTERM / 正常退出不丢。

### 4. 硬杀窗口用真杀进程测，不靠推断

`tests/test_write_behind.py` 起一个子进程：写入 N 条，然后 `os._exit(0)`——跳过 atexit、跳过所有 `finally`。两个变体：

- 先 `flush` 再退出 → 父进程从磁盘读到 **N 条**（已提交的行真的持久）；
- 不 flush 直接退出（写库人为放慢）→ 父进程读到 **N − pending 条**，且 `pending` 与差值一致。

第二个变体的价值在于它**承认丢失**：异步模式的持久性边界是「进程被 SIGKILL / 断电」，队列里的行会丢；这个窗口是有界的（队列深度 × 批次间隔），也是可数的。

### 5. 用三组对照量收益，门禁只量契约

`evals/persist_lab.py`：`off / sync / async` × `1 / 4 worker` × 2 轮，同批交替。判定计算「异步拿回了写库开销的百分之多少」，允许输出「没有收益」。

`--check` 是 CI 门禁，只断言与机器无关的部分：

1. 三组都 0 错误、都返回合法方案；
2. `off` 组落库增量为 0（开关真的生效）；
3. `sync` 与 `async` 组增量都等于成功请求数（异步在排空窗口内不丢写）；
4. 服务端回报的模式与实验分组一致（防止「改了环境变量但没生效」）。

吞吐、加速比、排空时间都不进门禁。

## 结果（本机一批，见 [persistence.md](../persistence.md)）

| 模式 | 1 worker 吞吐 | P95 | 4 worker 吞吐 |
| --- | ---: | ---: | ---: |
| `off` | 220–233 /s | 82–91 ms | 296–326 /s |
| `sync` | 44 /s | 184–188 ms | 133–143 /s |
| `async` | 127–133 /s | 92–94 ms | 267–273 /s |

异步相对同步 1 worker **2.96×**、4 worker **1.95×**，拿回约 **47%** 的写库开销，三组丢写均为 0。另一批独立运行是 5.5× / 45%：拿回比例稳定，绝对倍数不稳定。

**同批内**：关掉写库比同步写快 5.13×。这个绝对值在三次测量里是 2.48× / 11× / 5.13×，v0.9.0 那批与今天用旧脚本重跑的 7× 也对不上——差异来自磁盘、临时目录与后台负载，不是代码。所以报告只做同批内相对比较，这也是 ADR 0011 的结论。

## 被否决的方案

- **`BackgroundTasks`**：仍在请求进程内执行，进程被杀一样丢；没有批量、没有背压、没有可观测的 pending。它能解决的是「响应后做点事」，不是「可靠地写」，而这里要的恰恰是后者。
- **引入消息队列（Redis / RabbitMQ / Kafka）**：单机 demo 引入一个需要运维的外部依赖，换来的是「跨进程批量写」——而瓶颈是 fsync 次数，不是跨进程通信。等真的要多机部署再说。
- **换异步 SQLite 驱动**：SQLite 的写入最终是一次阻塞的 `fsync`，asyncio 无法把它变成非阻塞；异步驱动只是把同一个阻塞调用挪到线程池——那就是本方案在做的事，还多一个依赖。
- **直接删掉运行历史**：省事，也最快，但运行历史是可观测性、回归追溯与 `/api/stats` 面板的数据源。ADR 0011 的原话是「不该删掉，只该异步化」。

## 代价

- 多一个后台线程与一个队列（每进程），多一份 `persist_lab` 快照与报告，CI 多一道门禁（约 15 秒，三次短服务启动）。
- `async` 模式多一个必须被解释的持久性边界；它现在有测试和文档，但仍是运维需要知道的事。
- `storage.py` 从 130 行涨到约 300 行。这部分复杂度是用「一个模式可选」换来的，不是白送的。
