# ADR 0018 · 解释由知识库推导，而不是让模型自述

- 状态：已采纳
- 日期：2026-11-17
- 相关：[0003 精确检索优先于向量库](0003-exact-retrieval-over-vectors.md)、[0016 引用必须指向真实条目](0016-source-refs-must-resolve.md)

## 背景

一份方案只说了「16:26 去城墙拍摄」，没有说为什么是这里、为什么是这个时段。
用户只能猜这是系统算过的，还是模型随手写的。

最直接的做法是让模型在生成时多写一段 `rationale`。但这有三个问题：

1. **不可核对**：模型可以写「因为城墙适合唐制」，而它并没有读标签；
2. **成本与延迟**：解释会让每次生成的输出 token 变多，而解释本身不提高方案质量；
3. **会漂移**：同一份方案重跑一次，理由可能不同，历史对比失去意义。

## 决策

1. 新增纯函数 `explain.explain_plan(plan, request, kb)`，只读：
   - 请求的风格与 `must_include`；
   - 地点在 `locations.json` 中的标签、室内标记、客流与天气风险；
   - 与校验器**同一个** `light_window()` 的 NOAA 黄金窗口。
2. 解释放在 `PlanResult.explanations`，不写回 `Plan`。`Plan` 是 provider 的输出，
   `explanations` 是代码的派生视图；两者混在一起会让「模型说了什么」和
   「代码推断了什么」无法区分。
3. 每条理由必须指出证据（风格标签、分钟数、点名要求），不做没有数据的断言。
   部分覆盖只报实际分钟数与窗口外分钟数，并在不足 30 分钟时用「只有」。
4. 未知地点不抛异常，返回「无法给出可核对理由」；它通常意味着方案本身已硬失败。
5. 解释不新增模型调用，也不进入评分。

## 后果

- API `/api/plan`、CLI `plan`、Web 方案页与 `docs/examples.md` 都能看到逐块理由。
- 历史运行的解释与当时的 `kb_version` 一起留在 trace 里；知识库更新后，
  旧解释描述的是旧数据，不会被伪装成当前事实。
- 解释是通用的（风格、窗口、人流、天气），不是个性化文案；要更懂用户，
  需要补的是偏好与反馈数据，不是让模型编理由。
- 目前只解释 `shoot` 块。妆造/转场是拍摄排期的结果，单独编理由反而是噪声。

## 没有采纳的方案

- **在 prompt 里多要一个 `rationale` 字段**：不可核对、增加 token，且与「判定不交给模型」冲突。
- **生成后再调一次模型写解释**：多一次延迟与费用，理由仍不可核对。
- **把理由写进 `slot.notes`**：会覆盖模型自己的说明，也污染 `Plan` 与历史快照。
- **只给一个整体总结**：用户需要知道的是「这一块为什么排在这里」，不是一段泛泛而谈。
