# ADR 0002 · 校验器不经过模型

- 状态：已接受
- 日期：2026-11-12

## 背景

让 LLM「自己检查一下方案是否合理」是最省事的做法，也是最常见的做法。但它有两个致命问题：判定标准会随 prompt、模型版本、温度漂移；而且模型很难稳定地发现自己刚犯的算术和时序错误。

## 决策

「什么算可执行」由 `domain/constraints.py` 定义，由 `agents/validator.py` 用纯 Python 判定。模型只负责生成与修复，**不负责判定**。校验报告再转成精确的修复提示回喂给模型；修复结果只有在严格更优时才被接受。

## 理由

- 跨模型、跨 prompt 版本的分数可比，这是做回归测试的前提。
- 判定过程可单测：每条规则都有对应测试，改规则会立刻有反馈。
- 幻觉检测可以做得很硬：地点 id 不在知识库白名单里直接判失败，不依赖模型自述。
- 面试里能讲清楚「AI 系统里哪些部分不该交给 AI」，这比多写几个 prompt 有价值。

## 后果

- 正向：质量定义稳定；修复循环单调不降；评测有可信的判定源。
- 负向：规则需要人工维护，覆盖不了主观审美；新增业务约束要写代码。
- 缓解：把规则集中在一个文件，`RULES` 同时驱动校验器、文档和 `/api/rules`，避免多处不一致。

## 备选方案

LLM-as-judge（灵活但不可复现、有成本、难单测）；只做 schema 校验（能挡格式错误，挡不住「一天排五个外景」这类语义错误）。
