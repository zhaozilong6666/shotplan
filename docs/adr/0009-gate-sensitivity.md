# ADR 0009 · 用变异测试验证门禁本身

- 状态：已采纳
- 日期：2026-11-12
- 相关：[0002 校验器不经过模型](0002-validator-outside-model.md)、[0006 评分跨版本逐位一致](0006-scoring-determinism.md)、[0008 模糊测试与性能基准进门禁](0008-fuzz-and-benchmark-gates.md)

## 背景

阶段 3 结束时评测集是 80/80、均分 0.9788、CI 十道门禁全绿。这容易让人得出「质量有保障」的结论，但它只证明了**当前代码能通过当前检查**，没有证明**检查是有效的**：

- 一个永远返回 `score=1.0, hard_pass=True` 的校验器，会让所有用例通过、CI 全绿。
- 更隐蔽的是：悄悄删掉**一条**硬规则。故意犯错的 `naive` 对照组同时违反四到六条硬规则，`constraints` 维度按 `1 - 0.25×硬问题数 - 0.05×软问题数` 计算后早已被 clamp 到 0；少一条问题，对照组均分几乎不动，正式方案的指标完全不变。原先的门禁（均分下限、对照组不能更好）看不出异常。

我们用 `evals/mutation_lab.py` 注入 8 处受控故障实测：**旧门禁只拦住 4/8**。漏掉的四个全是校验端被削弱，其中「宽限改到 10^6 分钟」「所有地点 id 都视为存在」这两种改法，对照组的均分变化分别只有 0.0000 和 0.0005。

## 决策

### 1. 门禁函数只有一份

`evals.scorers.eval_gate_problems(good, naive, ...)` 是 CI 与变异实验室**共同调用**的唯一实现。实验室不复制阈值逻辑，否则将来改了 `run_eval` 而没改实验，门禁会悄悄失去验证。`tests/test_mutation_lab.py` 用对象身份断言这一点。

### 2. 给对照组加规则级覆盖下限

`naive` 是一份**已知缺陷清单**，不只是「低分样本」。门禁要求每条已知缺陷都被报出来：

| 规则 | 实测命中（80 用例） | 下限 |
| --- | ---: | ---: |
| `TRANSFER_BUFFER` | 198 | 100 |
| `UNKNOWN_LOCATION` | 186 | 90 |
| `BUDGET_EXCEEDED` | 69 | 30 |
| `TIME_OVERRUN` | 64 | 30 |
| `SHOOT_TOO_SHORT` / `NO_ALTERNATIVE` / `NO_SOURCE_REF` | 各 69 | 各 30 |

下限取实测值的一半左右：新增用例不会让门槛漂移，删掉一条规则必然让命中次数归零。另加两条聚合上限（对照组均分 ≤ 0.45、硬约束通过率 ≤ 0.30）和一条差值下限（good − naive ≥ 0.45），用于抓住「校验器整体失效」和「预算规则被放宽」。

### 3. 用变异测试给门禁做回归测试

- 8 个变异体分两类：3 个改**生成端**（不插转场、转场费 5000 元、删妆造块），5 个改**校验端**（预算容差、转场下限、时长宽限、地点白名单、直接返回满分）。
- 全部在进程内用 `ExitStack` + `unittest.mock.patch.object` 注入，**不修改任何源文件**；跑同一批 80 个用例、同一条流水线、同一个门禁函数。
- 每个变异体都必须被拒绝；退出后重跑基线并逐字段比对（只比确定性字段），验证回滚干净。
- 产物 `docs/mutation-report.md` 与 `evals/mutation.json` 都是生成的、不含时间戳/耗时/id；`--check` 同时校验「存活变异为 0」「回滚一致」「产物未过期」，作为 CI 第 11 道门禁。
- `docs/eval-report.md` 引用其中一处实例，写出「改动 → 分数下降 → 门禁拦截 → 回滚复原」的具体数字，满足阶段 4 的验收项，且不需要真实模型 API key。

## 后果

- 好：8/8 变异体被拦截（旧门禁 4/8）；「校验器被删一条规则」这种最难发现的回归现在会让 CI 失败。
- 好：评测报告里第一次出现可复核的失败—回滚实例，而不是只有一路绿灯。
- 代价：CI 多一步约 1–2 秒（8 个变异体 × 2 个 provider × 80 用例，全离线）。
- 代价：规则覆盖下限与对照组的**具体缺陷清单**绑定。若以后重做 `naive` provider，必须同步更新 `CONTROL_RULE_MIN_COUNTS` 并新增对应测试——这是有意的耦合：对照组换了一种坏法，门禁就该跟着换。
- 代价：展示页与评测报告都依赖提交的 `evals/mutation.json` 快照。它必须是确定性的，否则跨 Python 版本的一致性检查会变成噪声（同 ADR 0008 对基准数字的处理）。

## 备选方案与拒绝理由

- **只提高均分阈值 / 收紧硬约束通过率**：抓不到「好方案没变、只有尺子变了」的情况。实测四个漏网变异体的 good 均分全部保持 0.9788。
- **对校验器做纯单元测试**：仓库里已有 12 条规则的逐条测试，但那些测试断言的是函数行为，不是「CI 的门禁会不会因为规则被删而失败」。两者防的故障不同：前者防实现写错，后者防**测量链路失效**。
- **用 mutmut / cosmic-ray 之类通用变异测试工具**：会对整个源码做语法级变异、耗时长，还会引入依赖。这里的目的是验证一条具体的质量门禁，8 个语义明确的手工变异体更容易解释、更容易复现。
- **把变异体写进 CI 而不做回滚比对**：注入失败可能污染后续步骤。逐轮回滚 + 逐字段比对能保证实验本身没有副作用。
