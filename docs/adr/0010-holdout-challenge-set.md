# ADR 0010 · 盲测挑战集独立存放，不并入回归主集

- 状态：已采纳
- 日期：2026-11-12
- 相关：[0007 可行性判定在生成之前](0007-feasibility-before-generation.md)、[0008 模糊测试与性能基准进门禁](0008-fuzz-and-benchmark-gates.md)、[0009 用变异测试验证门禁本身](0009-gate-sensitivity.md)

## 背景

阶段 3 结束时有一条很自然但危险的改进建议：「失败案例库有 517 条记录，按问题码聚类，把没覆盖到的输入组合补进评测集」。

问题不在于补用例，而在于**补到哪里**。

`evals/baselines/v1..v6-naive.json` 是 12 / 36 / 50 / 60 / 70 / 80 用例六个时代的对照快照。它们之所以还能放在一起看，是因为主集变动缓慢且每次变动都有明确记录。一旦把自动挖掘出来的几百个用例塞进 `evals/cases/`：

- 所有历史基线立刻失去可比性——分数变化分不清是「实现变好了」还是「题目变简单了」；
- `run_eval` 的均分、对照组规则命中下限、修复实验的 69 个可满足 brief 等一整串数字同时变化，报告里任何一次回归都要重新解释；
- 更糟的是，挖掘器若读取了用例的**期望输出**，新用例会变成「照着答案写题」，评测集从此失去独立证据的价值。

同时，ADR 0009 解决了「尺子准不准」，但没有解决「题目是不是只见过这一套」。80/80 全绿仍然可能来自对着 80 道题调规则。

## 决策

### 1. 新增独立的一层证据，而不是扩大主集

`evals/challenge/cases.jsonl` 存放盲测用例，`run_eval.load_cases()` 只读 `evals/cases/`。

- 主集（80）：纵向回归基线，对 v1–v6 负责，变动需写进 CHANGELOG。
- 挑战集（200）：横向泛化检验，可以随知识库与失败库持续长大，不影响任何历史基线。

两者跑的是**同一条流水线、同一个校验器、同一对 provider**，只是用途不同。

### 2. 挖掘器不许看答案

`evals/case_miner.py` 的输入只有三样：失败案例库的记录、知识库的城市/风格/地点、以及主集 brief 的**规范化指纹**（仅用于去重）。它从不读取 `expect_hard_pass` / `expect_min_score`。

候选由确定性网格生成：5 城 × 5 风格 × 9 种压力配置 × 4 季轮换日期 = 225 个 brief，无随机数、无时间戳。每个候选跑 `good` 与 `naive`，同时满足五条才纳入：不与主集重复、`good` 可执行且得分 ≥ 0.70、`naive` 被判不可执行、两者得分差 ≥ 0.30。

### 3. 负向对照必须留在网格里

`conflicting`（同一地点既在 `must_include` 又在 `avoid`）是故意放进去的不可满足 brief。它应当被生成前可行性判定挡下、两个 provider 都停止生成，因此不构成可比较的一对方案。实测 25 个（5 城 × 5 风格）全部被筛掉。

门禁要求「被筛掉的数量不少于 25」。如果哪天这批候选突然全被纳入，说明前置判定被削弱了，CI 会把这当成**回归**，而不是当成覆盖率提升。

### 4. 产物与代码一起做一致性门禁

`--check` 重新挖掘一遍并逐字节比对 `cases.jsonl` / `case_mining.json` / `docs/case-mining.md`，同时断言纳入数、覆盖格数、新组合数、最小得分差与负向对照数量。改动校验器、知识库或 provider 导致某个组合不再被正确判定时，门禁在「挑战集内容变了」这一层直接失败，避免悄悄删用例蒙混过关。

## 实测结果

| 项 | 值 |
| --- | ---: |
| 候选 brief | 225 |
| 纳入挑战集 | 200 |
| 被筛掉（全部为负向对照） | 25 |
| 城市 × 风格覆盖 | 19/25 → 25/25 |
| 主集未覆盖的新格子 | 6 |
| good 硬约束通过率 / 均分 | 100% / 0.9881 |
| naive 硬约束通过率 / 均分 | 0% / 0.19 |
| 最小得分差 | 0.7687（要求 ≥ 0.30） |

`no_outdoor`（排除全部户外地点）与 `micro_budget`（贴近理论下限 400 元）两类共 50 个候选全部通过，顺带复核了「新增城市时室内备选地点硬编码」与 C24「紧预算超支」两处旧修复不是针对单条用例打补丁。

## 后果

**好处**：失败案例库从「只读的展示材料」变成真正驱动新用例的输入；主集与挑战集职责分离；每次改动校验器都能得到一次覆盖 25 个城市 × 风格组合的泛化复核。

**代价**：CI 多一道门禁（第 12 道），每次约 450 次离线流水线调用，实测耗时在秒级；仓库多三份生成产物与一份 ADR。

**边界**：0.9881 仍是离线规则 provider 的分数，不是新的效果声明。候选来自固定网格，覆盖的是组合多样性而非真实客户分布；对照组缺陷是构造的，`naive` 全挂只证明判定链一致，不证明真实模型会更差。接真实模型后，应当用同一套挖掘口径重新跑一遍，把模型真实犯错的组合追加进挑战集。

## 验证

```bash
python -m evals.case_miner --write   # 重新生成三份产物
python -m evals.case_miner --check  # CI 门禁
python -m pytest tests/test_case_miner.py -q
```
