# 修复循环实验报告

同一批 **42 个可满足 brief**，三种刻意构造的 provider，分别跑 `max_repairs=0`（首轮）与 `max_repairs=1`（允许修复一轮）。

## 方法

- `naive`：忽略修复提示，作为「修复无效」的对照组。
- `repairable`：首轮坏方案，带修复提示时产出合规方案，模拟我们期待真实模型具备的行为。
- `regressing`：首轮只有一个硬问题，「修复」后变得更糟，用于检验单调保护。
- 每次接受/拒绝都读 trace 里 `repair_*` 事件的 `accepted` 字段，不靠推断。

## 结果

| 实验组 | 首轮通过率 | 修复后通过率 | 一次修复成功率 | 修复轮次 | 接受/拒绝 | 均分变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `naive/repairs=0` | 0% | 0% | 0% | 0 | 0 / 0 | 0.19 → 0.19 |
| `naive/repairs=1` | 0% | 0% | 0% | 42 | 0 / 42 | 0.19 → 0.19 |
| `repairable/repairs=0` | 0% | 0% | 0% | 0 | 0 / 0 | 0.19 → 0.19 |
| `repairable/repairs=1` | 0% | 100% | 100% | 42 | 42 / 0 | 0.19 → 0.9744 |
| `regressing/repairs=0` | 0% | 0% | 0% | 0 | 0 / 0 | 0.6744 → 0.6744 |
| `regressing/repairs=1` | 0% | 0% | 0% | 42 | 0 / 42 | 0.6744 → 0.6744 |

## 结论

1. **修复提示确实能起作用**：`repairable` 首轮 0% → 修复后 100%，一次修复成功率 100%。
2. **修复不是免费的**：`naive` 忽略提示，42 次修复候选被拒绝，通过率没有提升。说明修复效果取决于 provider 是否真正使用校验报告。
3. **单调保护生效**：`regressing` 的 42 次「修复」全部被拒绝，均分保持 0.6744 → 0.6744，没有把方案改坏。
4. 因此「有修复循环」不等于「质量会变好」：必须有校验器判定、单调保护，以及像本实验这样量化的成功率指标。

## 边界

三个 provider 都是离线确定性构造，用来验证**机制**，不是真实模型能力评估。接入真实模型后应重跑本实验，把真实的一次修复成功率写进这里，并把典型失败加入 [failure-gallery.md](failure-gallery.md)。
