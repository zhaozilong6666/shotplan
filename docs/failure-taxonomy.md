# 失败模式与测量不确定性

数据来源：`evals/real-model.json`（`deepseek-v4.1-flash-1017`，80 例、并发 4）与 `evals/failures/cases.jsonl`（527 条构造失败记录）。本文只做分析，不重新调用模型。

## 一、先分清两套失败数据

把这两套混在一起谈是这类项目最常见的错误：

| 数据 | 来源 | 能说明什么 |
| --- | --- | --- |
| **527 条失败记录** | 由 offline 的 `naive` planner 构造出来 | 校验器能识别哪些违规、每类违规长什么样；**不代表真实模型的错误分布** |
| **4 个真实失败**（3 error + 1 硬失败） | 真实模型跑 80 例 | 真实模型会在哪里翻车；样本小，只能当线索 |

下面分开说。

## 二、构造失败：校验器覆盖了什么

527 条记录分布在 69 个用例、6 类硬规则上：

| 规则 | 条数 | 占比 | 典型信息 |
| --- | ---: | ---: | --- |
| `TRANSFER_BUFFER` | 198 | 37.6% | 从 A 到 B 只留了 0 分钟转场 |
| `UNKNOWN_LOCATION` | 186 | 35.3% | 引用了不存在的 `nonexistent_palace` |
| `BUDGET_EXCEEDED` | 69 | 13.1% | 总花费 3000，预算 1500 |
| `TIME_OVERRUN` | 64 | 12.1% | 总时长 660 分钟，可用 180 分钟 |
| `MISSING_REQUIRED_LOCATION` | 6 | 1.1% | 必去地点没出现在拍摄块 |
| `AVOIDED_LOCATION` | 4 | 0.8% | 用了被排除的地点 |

按用例分组：`normal` 230、`conflict` 180、`edge` 117。

**读法**：前两类占七成，是因为 `naive` planner 的策略就是“随便挑地点、不算路程”，这恰好说明校验器抓住了最常见的两类真实退化——编造地点和忽略转场。但它也暴露一个偏差：**构造失败集中在“结构性错误”，几乎不覆盖“语义合理但不可执行”的情况**（比如光线时段与拍摄内容冲突）。这是评测集的已知盲区，不是校验器的漏洞。

## 三、真实失败：4 个案例，3 个同一根因

### 3 个 error 全部是 schema 不合规

| 用例 | 错误 | 性质 |
| --- | --- | --- |
| C21 | `slot 1 missing fields: ['location_id']` | 缺必填字段 |
| C40 | `slot 1 has unknown activity 'costume'` | 自造枚举值 |
| C51 | 同上 | 自造枚举值 |

两个用例把「服装/妆造」写成了 `activity: costume`。schema 只允许 `makeup` / `travel` / `shoot`，模型把“服装准备”当成一个独立环节——这是**语义合理、schema 不容**的典型冲突。

### 唯一的硬失败：C62，得分 0.7625

方案能解析、能执行，但违反了硬约束。得分 0.7625 说明它在其他维度表现尚可——**这类“看起来不错的坏方案”才是最危险的**，也是当初决定用确定性校验而不是 LLM 自评的原因。

### 结构性问题：解析失败不进修复循环

`pipeline.py` 里解析是独立阶段：

```python
try:
    plan = parse_plan(...)
except ShotplanError as exc:
    result = _error_result(...)   # 直接返回，不进 repair
    return result
```

修复循环只在 `not report.hard_pass` 时启动，也就是**只有“解析成功但校验失败”才有第二次机会**。C21/C40/C51 这种字段级错误，恰恰是最容易被一句“请把 activity 限定为 makeup/travel/shoot，并补齐 location_id”修好的，却直接判死。

这是当前流水线最明显的设计缺口：**修复的覆盖面小于可修复问题的范围**。

## 四、测量不确定性：94.2% 这个数字有多稳

对 69 个用例做 2000 次自助法重采样（种子固定，报告可复现）：

| 指标 | 点估计 | 95% 区间 | 区间宽度 |
| --- | ---: | ---: | ---: |
| 硬约束通过率 | 94.2%（65/69） | 88.4% – 98.6% | 10.2 个百分点 |
| 平均得分 | 0.8424 | 0.793 – 0.882 | 0.089 |

三个直接推论：

1. **两轮 `deepseek-chat` 的 4.4 个百分点差异（89.9% vs 85.5%）落在噪声范围内**，不能据此说并发影响了质量，更不能据此排名。
2. 想可靠区分两个相差 3 个百分点的模型，n=69 远远不够；配对设计（同一批用例、同一温度）能把方差压下来，但仍需多轮重复。
3. 面试时正确的说法是“在 69 个用例上观测到 94.2%，95% 区间 88–99%”，而不是“通过率 94%”。**区间比点估计更诚实，也更难被追问倒。**

## 四点五、复现尝试：三个 error 没能复现

写完上面的分析后，我给解析失败加了一次有界修复（`repair_parse`，最多一次，与其他修复共用预算），然后只重跑了这三个用例：

| 用例 | 结果 | 修复次数 | 耗时 |
| --- | --- | ---: | ---: |
| C21 | `ok`，硬约束通过，得分 0.975 | 1（常规校验修复，非 `repair_parse`） | 133s |
| C40 | `ok`，硬约束通过，得分 0.830 | 0 | 76s |
| C51 | `ok`，硬约束通过，得分 0.830 | 0 | 49s |

**三个都没复现。** C21/C40/C51 这次都一次解析成功，新加的 `repair_parse` 一次都没被触发。

这个反证比原结论更重要：

1. 那 3 个 error 是 **temperature 0.2 下的采样长尾**，不是稳定缺陷。把它写成“模型不会用 schema”是过度归因。
2. 因此**不能声称** `repair_parse` 提升了真实通过率——它只在单元测试里被验证过（构造一个先返回非法 payload 的 provider，断言恰好重试一次且总调用数为 2）。
3. 但它仍然值得保留：它是**兜底**，不是优化。代价是一次修复预算，收益是把“字段写错”从不可恢复变成可恢复；是否划算要看长期发生率，而 69 个用例的样本量还测不出来。
4. 真正的教训是评测口径：**单轮里出现的 error 必须先复现，再归因**。这次如果直接写“修复了解析缺陷，通过率从 94.2% 提升到 X%”，就是拿噪声当成果。

## 六、这份分析的边界

- 真实失败只有 4 例，任何“根因占比”都不具统计意义，只能作为改进线索。
- 527 条构造失败反映的是 `naive` planner 的策略偏差，不能外推为“真实模型的错误分布”。
- 自助法区间衡量的是**用例抽样**不确定性，不包含模型采样（temperature）与上游服务波动。
