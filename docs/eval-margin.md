# 每条 brief 留了多少余量

E19 把每个规则常量扰动 ±50%，最多影响 3 条 brief。要么常量在一个平坦区间里，要么方案会自适应——时间紧就少排一个地点，于是「通过」不变、方案变形。

第二种解释有个可检验的推论：方案应该被排得很满（余量小），而调整的旋钮是「整个地点」而不是分钟。下面统计 80 条 brief 的 `hours×60` 与方案实际跨度之差。

| 分组 | 条数 | 通过 | 余量（中位 / 最小 / 最大，分钟） |
| --- | ---: | ---: | --- |
| conflict | 23 | 23 | 0 / 0 / 0 |
| edge | 16 | 16 | 0 / 0 / 0 |
| infeasible | 11 | 0 | — |
| normal | 30 | 30 | 0 / 0 / 0 |
| **全部** | 80 | 69 | 0 / 0 / 0 |

## 结论

可行 brief 的余量中位数是 **0 分钟**，69 条 brief 的余量不超过 15 分钟（也就是排到了上限）。

**余量为 0 不是巧合，是设计。** planner 的最后一块拍摄会拉伸到结束时刻（`duration = max(duration, end_limit - cursor)`），所以只要排得下，方案必然用满。「余量」在这个系统里因此不是变量，而是一个恒等于 0 的结果——它不能用来解释敏感性，只能说明方案没有留白。

真正限制灵敏度的是粒度。方案能调的最小单位是一个地点（60 分钟以上），而常量扰动带来的是 5–20 分钟：跨不过那一档，所以通过率不变、地点数也不变。E19 里那 3 条失败的 brief，正是被压到 `SHOOT_TOO_SHORT` 下限的边界样本。

这也解释了 E18 为什么在 8 个城市都测不出差别：不是城市结构的问题，是任何小于一个地点的变化都不会反映到结果里。

## 不可行的那些卡在哪

- `INFEASIBLE`：11 条

这些 brief 的通过与否由可行性判定决定，和排期常量无关——所以它们不会因为参数扰动而改变，这在 E19 里表现为「一半的样本永远不变」。

## 局限

余量是 `hours×60 − 方案跨度`，而方案跨度从第一个时间块算起，不含开始前的等待。所以余量不是「用户可用的空闲」，只是「方案之后还剩多少」。
