# 真实 HTTP 服务压测

> 由 `python -m evals.http_load --write` 生成本机快照。数字与机器相关，**不进 CI 门禁**。

## 为什么还要做这一层

之前的 `loadtest.py`（进程内线程）、`scaling.py`（进程池）、`benchmark.py`（单次调用）测的都是 Python 函数，没有 HTTP 解析、ASGI 中间件、完整 plan + trace 的 JSON 序列化、loopback 网络栈，也没有**多个 OS 进程同时写同一个 SQLite 文件**。
这一层启动真正的 `uvicorn`，用 `httpx` 走 `127.0.0.1` 发 `POST /api/plan`，把「服务」而不是「函数」放到压力下面。

环境：Python 3.13.14 / Windows / 18 逻辑核；离线 mock provider，无外部网络调用。

## 单 worker 的并发阶梯

| 并发 | 请求 | 吞吐 (/s) | P50 / P95 (ms) | 错误 | 落库 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 200 | 116.38 | 7.25 / 12.28 | 0 | 200/200 |
| 4 | 200 | 238.27 | 15.4 / 21.62 | 0 | 200/200 |
| 8 | 200 | 250.66 | 29.89 / 39.9 | 0 | 200/200 |

## worker 扩展曲线（并发固定 8）

| workers | 请求 | 吞吐 (/s) | 相对 1 worker | P95 (ms) | 错误 | 启动 (s) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 200 | 250.66 | 1.00× | 39.9 | 0 | 1.82 |
| 2 | 200 | 280.37 | 1.12× | 65.14 | 0 | 2.58 |
| 4 | 200 | 129.62 | 0.52× | 149.53 | 0 | 5.61 |

相对 1 worker 的倍数以**同一批并发 8 请求**为基准（表中的基准吞吐取自单 worker 并发 8 场景）。
启动时间包含 uvicorn 进程创建与 `spawn`/`fork` 开销，不计入请求计时。

## 与进程内数字对照

- `docs/loadtest.md`：进程内线程并发 8 约 **310/s**，p95 约 **27ms**。
- `docs/scaling.md`：进程池纯函数吞吐约 **数千次/秒**。
- 这里单 worker 并发 8 的吞吐与进程内同量级但略低（多了 HTTP/JSON/网络栈与一次完整 SQLite 提交），P95 则从约 27ms 变成几十到上百 ms；这才是对外提供服务时真正能拿到的量级。

## 多 worker 为什么没有线性提速

实测 4 worker 的吞吐是单 worker 的 **0.52×**，P95 从 **39.9 ms** 变为 **149.53 ms**。曲线最好的一档是 **2 worker（1.12×）**，继续加 worker 反而回落。

这不推翻 `docs/scaling.md` 里「纯计算受 GIL 限制」的结论，而是补上了一个前提：**瓶颈会随架构层变化**。进程池实验里各 worker 不共享任何状态；真实服务里每个 `/api/plan` 都要写一条 run 记录，4 个 uvicorn worker 抢的是同一个 SQLite 文件，WAL 同一时刻只允许一个写者，跨进程写锁与进程协调开销会盖过并行收益。

换句话说：要真正在多核上扩展，先得把共享 SQLite 从关键路径上移开（独立 DB 服务、写队列或按进程分片），再加 worker；只加 worker 只会放大争用。这条结论只有把服务真正跑起来才看得见，进程内微基准给不了。

数据来自本机 loopback 小样本，不外推到容器化或带真实模型延迟的生产环境。

## 门禁检查什么

`python -m evals.http_load --check` 只跑一组稳定场景（1 worker、并发 4、40 次请求），断言：

1. 所有请求都收到响应；
2. 全部返回 HTTP 200 + `status=ok` + `validation` 块；
3. `GET /api/stats` 的 `total_runs` 增量等于成功请求数（**0 丢写**）；
4. P95 不超过 3000ms 的宽松上限，只用于抓「服务挂住」。

吞吐、P50/P95 的绝对值、worker 加速比**都不做断言**：它们随 CPU、磁盘与 CI 机器负载变化，把它们写进门禁只会制造偶发红（ADR 0008 的原则，扩展性门禁已因此修过一次）。

## 边界

- 单机 loopback、无 TLS、无反向代理、无真实模型延迟；离线 provider 是纯 CPU 计算。
- 这不是生产 QPS，也不能外推到容器化部署；它只说明「服务层的开销量级」和「多进程写 SQLite 仍然不丢数据」。
- 快照 `evals/http_load.json` 是本机一次运行的结果，重跑会变化；展示页读的是这份已提交快照。

## 复现

```bash
python -m evals.http_load --check   # CI 门禁
python -m evals.http_load --write  # 重跑完整矩阵并刷新报告
```
