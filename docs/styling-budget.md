# 妆造是唯一能让出时间的块

> 2026-11-17。起因：短预约的真实输出是「85 分钟妆造 + 5 分钟拍摄」。
> 校验器只软报一句 `SHOOT_TOO_SHORT`，方案照样交付——这是排程缺陷，不是规则太严。

## 1. 真实输出说明了什么

同一天、同一个模型、两条 1.5–2 小时的 brief：

| 用例 | 模型写出的时间轴 | 结果 |
| --- | --- | --- |
| C46（洛阳 1.5h 民国） | 妆造 85 分钟 → 拍摄 **5 分钟** | `SHOOT_TOO_SHORT`，得分 0.83 |
| C22（西安 2h 宋制） | 妆造 70 + 换装 30 → 拍摄 **20 分钟** | `SHOOT_TOO_SHORT`，得分 0.855 |

模型没有算错，它照着知识库里「民国妆造 60 分钟 + 换装 25 分钟」的标准时长填，
发现总时长装不下，于是把缺口全部压给拍摄，还在 notes 里写明
「因总时长仅 90 分钟，妆造 85 分钟后仅能安排 5 分钟快拍」。

**它知道自己在做什么，只是没权力改妆造时长。**

## 2. 谁该让时间

预约时长是用户给的预算，拍摄是用户付钱买的东西。三块时间里：

| 块 | 能不能压缩 | 为什么 |
| --- | --- | --- |
| 转场 | 不能 | 距离决定，压了就变成瞬移 |
| 拍摄 | 不能 | 压它等于少给货 |
| 妆造 | **能** | 化妆师加快手速是行业常态，代价是效果，可以明说 |

所以规则写成：`styling_minutes_for(standard, hours) = min(standard, max(60, 35% × 总时长))`。
这条公式原本只存在于离线 mock（`agents/mock.py`），现在提到 `domain/constraints.py`，
线上模型与离线规划器共用同一个定义——否则两边对「压缩」的理解会分叉。

## 3. 修复方式：代码改，不让模型再猜一次

`timeline.compress_styling_for_shoots()`：

1. 找一个短于门槛的拍摄块，往前找**连续的妆造段**（真实输出常把它拆成「妆面 60」+「换装 25」两块）；
2. 按上面的公式算出这段最多该占多少分钟，把差额从离拍摄最近的那块往回扣；
3. 拍摄块的**结束时间不动**，开始时间前移；
4. 只有校验不劣化才采纳（和光线对齐、尾段补齐同一条规矩）。

两处诚实性要求，缺一不可：

- **改时间就必须改文案**：模型写的「仅能安排 5 分钟快拍」如果留着，方案会自相矛盾。
  代码把标签里等于旧时长的数字改掉，并在 notes 里追加「该块已由 5 分钟补足为 30 分钟」。
- **摘要跟着块走**：`styling.makeup_minutes` 同步扣减，避免方案抬头写 100 分钟、下面只有 90 分钟。

## 4. 效果

| | 修复前（80 例） | 修复后（80 例） |
| --- | ---: | ---: |
| `SHOOT_TOO_SHORT` | 4 例 | **0 例** |
| 硬约束通过 | 80/80 | 80/80 |
| 平均得分 | 0.9346 | 0.9280 |

逐例核对比总数可靠：上一轮被点名的 **C22 / C43 / C46 / C53 这一轮都没有再触发**
`SHOOT_TOO_SHORT`（C43 这次报了另一条 `STYLE_MISMATCH`，与拍摄时长无关）。
均分从 0.9346 到 0.9280 是采样波动，两次的 95% 区间重叠，**不构成退步证据**。

**但「4 → 0」不能当成比率**。对同样这 4 例各跑 3 轮（12 次调用）复核：

| 指标 | 12 次调用 |
| --- | ---: |
| 硬约束通过 | **12/12** |
| `SHOOT_TOO_SHORT` | **1 次**（8.3%） |
| `STYLE_MISMATCH` | 1 次（与本次改动无关） |

所以准确的结论是「**同类问题大幅下降，但没有清零**」，而不是「已经解决」。
剩下的那一次落在修复范围之外：压缩只处理「妆造段紧贴拍摄块」的情况，
如果模型在两者之间插了一个 `rest`（把换装写成休息），或者拍摄块不在末尾，这段代码就不动它。

单例复现（同一 brief、不同次采样）：

```
C46 修复前：14:47-16:12 妆造(85) 16:12-16:17 拍摄(5)      -> SHOOT_TOO_SHORT
C46 修复后：09:00-10:00 妆造(60) 10:00-10:30 拍摄(30)     -> 无问题
C22 修复前：14:46-15:56 妆造(70) + 15:56-16:26 换装(30) + 16:26-16:46 拍摄(20)
C22 修复后：14:56-16:26 妆造(90) + 16:26-16:56 拍摄(30)    -> 无问题
```

C22 只压缩了 10 分钟而不是按上限压到 60：缺口多大就补多少，不借机把妆造砍到最短。

## 5. 边界

- 只处理「妆造段紧贴拍摄块」的情况；中间隔着转场的，留给修复循环——移动后续块是重叠的来源。
- 只压缩 `makeup`，不碰 `rest`。模型有时把换装写成 `rest`，那种情况这次不处理（C22 修复后
  的妆造是单个 90 分钟块，正是靠只算 makeup 段才没误伤休息）。
- 单次采样。机制是确定性的（同样的输入必然得到同样的输出），但「4 例降到 0 例」这个比例
  需要多轮重复才能当比率用。
- **没有解决可行性判定**：1.5 小时能不能拍，取决于愿不愿意接受简妆。现在的做法是
  「先给一个压缩过妆造、拍摄达标的方案」，而不是「先告诉你这个预约很紧」。
  后者属于协商层（`negotiation.headroom()`），这次没动。
