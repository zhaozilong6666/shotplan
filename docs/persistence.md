# 写入异步化：把运行历史移出请求关键路径

> 由 `python -m evals.persist_lab --write` 生成本机快照。数字机器相关，**不进 CI 门禁**。

## 上一版留下的问题

[worker-bottleneck.md](worker-bottleneck.md)（v0.9.0）用开/关对照实验确认了「同步写运行历史是请求关键路径上最大的单项开销」，并给出建议：**把写入异步化，而不是删掉历史**。建议当时没有实现，也没有验证。
这一版实现了，并且用同一个压测框架量它到底还回多少。

## 三个实验组

同一份产品代码，只改 `SHOTPLAN_PERSIST_MODE`：

| 组 | 行为 | 可交付？ |
| --- | --- | --- |
| `off` | `run_plan(store=None)`，完全不写 | 否，没有历史就没有可观测性与回归追溯 |
| `sync` | 响应返回前提交（v0.9.0 的行为，当前默认） | 是 |
| `async` | 交给进程内写线程，批量提交，退出时排空 | 是，代价是硬杀时的丢失窗口 |

环境：Python 3.13.14 / Windows / 18 逻辑核；并发 8，每组 150 次请求、重复 2 轮取中位数，三组在同一批内交替执行。

「排空」一列是最后一个响应返回之后，行数补齐所花的时间——异步的代价在这里，不在吞吐里。

## 结论

**写入异步化确实把成本还回来了**。

- 同步写库的代价：关掉写入后 1 worker 快 **5.13×**、4 worker 快 **2.25×**。这是上限，不是可交付状态（没有历史）。
- 异步写库的收益：相对同步写入，1 worker **2.96×**、4 worker **1.95×**，即拿回了写库开销的 **47%**。
- P95：同步 186.12ms → 异步 92.86ms（1 worker，中位数）。
- **没有丢写**：三组都满足「每个被接受的请求最终都落库」，异步组是在排空窗口内等齐的。

## 实现要点

1. **一个进程一个写线程**（`RunWriter`），不是一请求一个。SQLite 只有一个写者，让 N 个请求线程去抢锁，不如让它们把行交给一个线程批量提交。
2. **批量提交**：`save_many` 在一个事务里 `executemany`，32 行一次 fsync，而不是 32 次。
3. **不丢**：队列满时不丢行，退化为同步写并计数（`sync_fallbacks`）；批次失败重试一次，仍失败则计入 `failed` 而不是杀掉线程。
4. **可观测**：`/api/config` 在 async 模式下暴露 `submitted / written / pending / batches / max_batch / sync_fallbacks`，队列积压是可见的。
5. **退出排空**：FastAPI `lifespan` 在 shutdown 时 `flush`，SIGTERM 不丢；`os._exit` / 断电会丢队列里的行——这个窗口被真实测量，不靠推断。

## 门禁检查什么

`python -m evals.persist_lab --check` 跑三个短场景（1 worker，每组 30 次），断言的是**契约**而不是速度：

1. 三组都 0 错误、都返回合法 `status=ok` 方案；
2. `off` 组 `total_runs` 增量为 0——开关真的生效；
3. `sync` 与 `async` 组增量都等于成功请求数——异步模式在排空窗口内不丢写；
4. 服务端回报的模式与实验分组一致——防止「改了环境变量但没生效」的自欺欺人。

吞吐、加速比、排空时间与结论文字都不进门禁（[ADR 0008](adr/0008-fuzz-and-benchmark-gates.md)）。

## 边界

- 异步只是把**等待**移出请求路径，并没有减少写库的总工作量：同样的行、同样的 fsync，只是改成每 32 行一次提交，并由后台线程承担。
- 每个 worker 进程各有一个写线程和一个队列，跨进程仍然争用同一个 SQLite 写者；worker 越多，这条争用越明显。真正的多机方案需要独立写服务或消息队列。
- 离线 mock provider 下服务本身很快，写库占比因此被放大；接入真实模型后，网络延迟会稀释这个收益，比例会下降。
- **跨批次不可比**：同一台机器上，v0.9.0 那批关掉写库只快 2.48×，本批是 11×；用未修改的旧脚本今天重跑得到 7×。差异来自磁盘 / 临时目录 / 后台负载，不是代码。所以本报告只做**同批内**的相对比较，绝对吞吐不进任何结论。
- 异步模式的持久性边界是「进程被 SIGKILL / 断电」：队列里未提交的行会丢。测试里用 `os._exit` 真实杀进程量过这个窗口（tests/test_write_behind.py），不是靠推断。优雅退出（SIGTERM / lifespan shutdown）会先排空，不丢。
