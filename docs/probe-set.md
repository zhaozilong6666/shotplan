# 边界探针：单边改动必须被检出

主集看不见多数常量的 ±50% 变化（E19），E20 解释了原因：方案总是排满，而最小调整单位是一个地点。这两组探针反过来构造——每条 brief 都卡在**某一条规则**的边缘。

每个场景跑同一批 brief：`baseline` 什么都不改；`one-sided` 只在校验端收紧规则，生成端不变；`both-sides` 在所有绑定该常量的模块里同步收紧。

## transfer（12 条）

转场下限收紧到 30 分钟，生成端仍排 20。

| 场景 | 通过 | 失败的编码 |
| --- | ---: | --- |
| `baseline` | 12/12 | — |
| `one-sided` | 0/12 | TRANSFER_BUFFER |
| `both-sides` | 12/12 | — |

## budget（4 条）

预算容差收紧到 −50 元，方案成本刚好等于预算。

| 场景 | 通过 | 失败的编码 |
| --- | ---: | --- |
| `baseline` | 4/4 | — |
| `one-sided` | 0/4 | BUDGET_EXCEEDED |
| `both-sides` | 0/4 | BUDGET_EXCEEDED |

## 为什么这个对比重要

同一个常量出现在多个模块里，因为 `from constraints import X` 会把值复制成模块自己的名字。只改一份不是「改了规则」，而是让两个组件对规则的理解产生分歧。

`transfer` 的 `one-sided` 让 12 条探针失败——生成端排出 20 分钟转场，校验端要求 30，每一条都被拦下。`both-sides` 则 12/12 通过：两端一致时，收紧规则本身不破坏方案。

`budget` 的两行相同（0/4），因为生成端根本不读容差——它只花钱。这种「规则只有一侧」的常量，单边改动就是全部改动，不存在不一致。

**真正的风险不是「常量取多少」，而是「改常量时漏了一处」。**探针让这种遗漏立刻变红，代价只有十几条 brief 的运行时。

## 它在门禁里断言什么

```
每组 baseline       全部通过  —— 否则探针没有卡在它声称的边界上
每组 one-sided      全部失败  —— 否则单边改动不会被发现
transfer both-sides 全部通过  —— 否则收紧规则本身就有问题
```

三条都成立时，这组样本才配叫「探针」。任何一条不成立，先修探针，再看别的。

## 局限

`TIME_OVERRUN` 还没有探针：planner 不会主动超时，要构造这条边界得注入一个超长的方案，方式与这两组不同（不是收紧规则，而是伪造生成结果）。留作后续。

探针集不进主集、不进 80 条评测，改动它们不影响基线分数。
