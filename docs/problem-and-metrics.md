# 问题定义与指标

一个评测体系如果没有说清楚「什么算好」，那么跑出来的分数只是自我安慰。这份文档把每个数字背后的理由写清楚，方便被质疑、被修改。

## 问题边界

**输入**：一段模糊 brief（城市、日期、可用小时数、预算、想要的风格、偏好、排除项）。
**输出**：一份小时级方案（时间块序列、妆造配置、总花费、备选、假设、知识库引用），或一份**结构化的不可行说明**。
**判定**：需求是否可满足；若可满足，方案是否**可执行**，以及质量有多高。

「可执行」的定义不是文笔，而是物理与商业约束：时间不能重叠、妆造必须先于拍摄、跨景点要留出转场、预算不能超、地点必须真实存在。

## 为什么这些是硬约束

| 规则 | 阈值 | 依据 |
| --- | --- | --- |
| 时间不重叠 | — | 重叠行程现实中不可能执行，是自由文本生成的高频错误 |
| 总时长 | 预约时长 + 15 分钟 | 15 分钟是收尾容差；再多就要加钱或砍环节 |
| 妆造在前 | — | 汉服拍摄不成立的前提 |
| 转场缓冲 | 20 分钟 | 西安景区之间移动 + 补妆 + 器材搬运的保守下限 |
| 预算 | 不允许超出 | 预算是用户给的硬约束，不是建议值 |
| 地点存在 | 知识库白名单 | 拦截模型编造景点名 |

**为什么预算取 `max(声明总计, 时间块求和)`**：模型可能把每个时间块都填上真实价格，却在汇总字段写一个偏小的数字。只信声明值等于给了一个绕过约束的口子。

## 生成前的可行性下限（ADR 0007）

在调用任何 provider 之前，先用纯 Python 判断 brief 是否可能满足：

- 最低预算 = 最简妆造 300 + 最低场地 0 + 转场 50 = **350 元**（从知识库动态计算）
- 最短时长 = **1.5 小时**（妆造 60 分钟 + 转场 20 分钟 + 一次可交付拍摄）
- 城市必须存在于知识库；`must_include` 与 `avoid` 不得冲突

不满足时返回 `status="infeasible"`，逐条给出原因、缺口、修改建议与理论下限，**不生成方案**。这是理论下限而非商家报价：知识库价格变化会自动重算，但仍不代表实时供给。

## 为什么这些是软约束

软约束代表质量而非可行性：拍摄块过短（< 60 分钟不值得架灯）、黄金光线被浪费、没有雨天备选、缺少引用、风格与场景不搭。它们不否决方案，但会拉低分数——因为它们正是「能用」和「好用」的差别。

黄金光线按季节粗分：冬季 15:00–17:00、春秋 16:00–18:00、夏季 17:00–19:00。这是刻意的简化：真实日落需要经纬度和日期查表，但对「傍晚是否安排了外景」这个判断，季节粒度已经够用，而且完全可复现、不依赖外部 API。

## 评分维度与权重

| 维度 | 权重 | 计算 |
| --- | --- | ---: |
| `constraints` | 0.40 | 每个硬问题 −0.25、软问题 −0.05，下限 0 |
| `budget` | 0.20 | 未超支为 1；超支按超出比例线性扣分 |
| `traceability` | 0.15 | 0.6 × 引用数达标率 + 0.4 × 带引用的时间块比例 |
| `light` | 0.15 | 黄金窗口内外景拍摄分钟数 / 窗口长度 |
| `completeness` | 0.10 | 备选、假设、妆造配置、逐块备注、时间块数量 五项均值 |

权重总和必须为 1，由 `test_validator.py::test_score_weights_sum_to_one` 强制检查。分数用 `math.fsum` 聚合并规整到 6 位小数，保证 3.10–3.13 上逐位一致（ADR 0006）。

**为什么 `constraints` 占 0.40**：可执行性是门槛，不是加分项。硬约束单独用 `hard_pass` 做布尔门禁，评分里再给它最高权重，是为了让「勉强通过但一堆软问题」和「干净的方案」拉开差距。

**为什么硬约束失败时仍计算分数**：CI 需要连续量来检测退化。只有布尔通过/失败的话，一次改动让方案从「差一点」变成「差很多」不会被发现。

## 用例设计

36 个用例分四组，都是 brief 而非固定输出：

- `normal`（13）：常规需求，覆盖四季、五种风格、时长、人数、多风格与指定地点。
- `conflict`（10）：约束冲突——时间紧、预算紧、排除热门景点、排除全部外景、逼近最低预算。
- `edge`（7）：1.5 小时极短预约、12 小时上限、季节边界、未指定风格、10 人团体。
- `infeasible`（6）：预算不足、时长不足、未知城市、约束互相矛盾、多原因叠加。

每个用例带 `expect_hard_pass` 与 `expect_min_score`（`infeasible` 组额外带 `expect_infeasible`）。分数下限按分组递减，因为约束越紧，方案质量天然越难做到完美。例如 C10（1.5 小时）会如实触发 `SHOOT_TOO_SHORT`——这是正确行为，不该为了「全绿」把阈值调低到掩盖它。

**不可满足需求如何计分**：正确性为「停止生成并返回结构化原因」→ 1.0 分；硬凑一份违规方案 → 0.0 分。可行性判定发生在生成之前且不确定于 provider，所以两个 provider 在这 6 个用例上共享结论；区分度由其余 30 个用例提供。

## 对照组

`naive` provider 故意忽略时间、转场、预算、溯源并编造地点。在 36 个用例上的表现为硬约束通过率 **16.7%**、均分 **0.325**（其中 6 个不可满足用例因共享 preflight 而正确拒绝）；规则版 provider 为 **100%** / **0.9811**，差值 **0.6561**。

诚实说明：离线规则 provider 是照着规则写的，因此高分在预期之内。这套评测真正的压力测试发生在阶段 4 接入真实模型之后——那时 `naive` 与 `good` 之间才会出现有意义的中间地带，也是 prompt 版本对比实验的用武之地。现阶段它的价值是证明**测量工具本身有效**：如果连一份明显不可执行的方案都能拿高分，任何后续结论都不可信。

## 已知缺口

- 可行性下限来自静态知识库，不含实时票价、闭馆、天气与商家档期。
- 没有人工标注的黄金标准答案，因此不评估「方案好不好看」这类主观质量，只评估可执行性与可追溯性。
- 真实模型的成本/延迟对比尚未实测；报告中的估算成本在离线模式下恒为 0。
