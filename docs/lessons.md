## L001 · 强杀长跑留下临时库

- **症状**：`D:/WorkBuddy/temp` 多出 789MB `shotplan-soak-*`；四小时运行只有 live 计数，没有完整报告。
- **根因**：`TemporaryDirectory` 依赖正常退出清理；进程被 `TaskStop` 强杀时 `finally` 不执行。
- **修复**：从残留 SQLite 补算服务端分位（164,956 行、P99.9 5.09ms），删除库；`soak` 启动时按 `soak.pid` 清理死进程目录，无 PID 的目录超过 12 小时才删。
- **验证**：`docs/soak-partial-4h24.md`；短跑结束后无残留目录。
- **防复发**：长跑启动写 PID；强杀后下一次启动自动回收；手工清理入口写进本文。

## L002 · ICS 缺 VTIMEZONE

- **症状**：导出只有 `DTSTART;TZID=Asia/Shanghai`，严格日历客户端可能拒绝或按错误时区解析。
- **根因**：只考虑了宽松解析器；`TZID` 引用没有自带时区定义。
- **修复**：加入 `VTIMEZONE`（`+0800`，无夏令时），保留 `TZID`。
- **验证**：`tests/test_export.py` 断言 `BEGIN:VTIMEZONE`、`TZID`、`TZOFFSETTO:+0800`。
- **防复发**：导出格式变更必须同时更新结构测试，不依赖某个客户端碰巧能读。

## L003 · 长跑状态的全表聚合

- **症状**：`soak` 每 30 秒调用 `RunStore.summary()`，在 16 万行时做多次全表聚合。
- **根因**：实时状态只需要行数，却复用了给面板用的重量级统计。
- **修复**：新增 `RunStore.count()`，状态和结束统计改用 `COUNT(*)`。
- **验证**：`tests/test_storage.py` 断言 `count()` 与 `summary()["total_runs"]` 一致。
- **防复发**：测量工具自身的 SQL 开销要按“被测路径”对待，状态查询不跑聚合。

## L004 · soak 默认与实验结论矛盾

- **症状**：E29 已证明 `batch` 下 2 worker 起出现 30s 尾延迟，`make soak` 仍默认 4 worker。
- **根因**：改了部署建议，没有同步默认入口。
- **修复**：`make soak` / `soak.py` 默认 1 worker；`docs/soak-index.md` 旧 4 worker 报告标为历史基线。
- **验证**：新默认 30 分钟 1154/1154、0 慢请求。
- **防复发**：默认值变更必须同时改 Makefile、argparse 默认、索引和部署文档，四处缺一不可。

## L005 · 系统睡眠伪装成服务卡死

- **症状**：高强度长跑第 7 分钟到第 23 分钟没有任何采样，看起来像服务冻住。
- **根因**：Windows 进入睡眠，进程被挂起；事件日志有 Kernel-Power 会话切换。
- **修复**：`soak` 在 Windows 调用 `SetThreadExecutionState` 阻止系统睡眠（不阻止关机）。
- **验证**：后续 120 分钟运行无时间空档。
- **防复发**：先查 OS 事件日志，再怀疑应用；长跑默认 keep-awake。

## L006 · README 材料数量写错

- **症状**：标题写“十四份可核查的材料”，正文列了 15 项。
- **根因**：新增第 15 项时只加列表，没有改标题和作品集文案。
- **修复**：README 改为“十五份”，作品集一页纸同步为 15 份。
- **验证**：人工核对 1–15 编号连续；`doc-claims` 通过。
- **防复发**：新增/删除材料时把“数量”当作一个字段一起改，不靠记忆。

## L007 · 单写者 sidecar 的否定结果

- **症状**：4 worker + 单写者 sidecar 仍出现 11 次 `ReadTimeout`/30 分钟，最大 30s；1 worker + 同 sidecar 0 错误、最大 512ms。
- **根因（假设被推翻）**：此前把多 worker 尾延迟主要归因于多进程 SQLite 写竞争；把写者收敛到一个进程后，4 worker 的尾延迟仍在，说明写竞争不是唯一原因。
- **修复**：不把 sidecar 设为默认；默认仍是 `batch + 1 worker`；sidecar 保留为可选实验。
- **验证**：`docs/single-writer.md`；4 worker 30,650 请求/11 错误，1 worker 11,957/0 错误。
- **防复发**：架构变更必须做“改前/改后 + 1/4 worker”对照，不能只验证新组件在单 worker 下干净就宣布解决。

## L008 · `off` 模式把成功请求算成丢写

- **症状**：4 worker、`off`、20 分钟的 soak 报告写“丢写 25,962”，恰好等于全部成功请求。
- **根因**：`lost = max(0, ok - rows)` 假设所有模式都落库；`off` 模式 `rows=0` 是预期行为，不是丢写。
- **修复**：`lost` 在 `off` 模式固定为 0；报告显示“—（off 不落库）”，不冒充 0 丢写。
- **验证**：重生成 `docs/soak-off-4w-20m.md`，丢写行显示“—（off 不落库）”。
- **防复发**：指标公式必须写明前置条件；`rows=0` 在 `off` 下是契约，不是异常。

## L009 · keep-alive 复用伪装成服务端尾延迟

- **症状**：4 worker、`off`、带 keep-alive 的 20 分钟出现 4 次 30s 超时；禁用连接复用后同样配置 0 错误、最大 271ms。
- **根因**：soak 所有线程共享一个 `httpx.Client`，连接复用到 4 个 worker；陈旧/半关闭连接把客户端等待放大成 30s，服务端中间件却记录不到 >1s 的请求。
- **修复**：soak 增加 `--no-keepalive`；诊断时把“客户端连接复用”作为控制变量，不和服务端尾延迟混在一起。
- **验证**：`off` + `--no-keepalive` 13,449/13,449，0 错误；`batch` + `--no-keepalive` 仍有 4 次超时，说明持久化路径还有独立问题。
- **防复发**：任何“服务端慢”的结论，先看服务端 `X-Server-Duration-Ms`/慢日志；没有服务端慢记录就不要归因于应用。

## L010 · 分段前把 30s 的剩余时间都算成 store.save

- **症状**：4 worker + batch 的慢请求服务端总耗时 30,352ms，但同一个请求的 `pipeline_ms` 只有 2.2ms。
- **根因**：没有在响应里带分段耗时，之前只能从总时长猜是 SQLite、uvicorn 还是客户端；当时把剩余时间归给 `store.save`；后续分段证明这个归因也不成立。
- **修复**：`/api/plan` 返回 `X-Pipeline-Duration-Ms`，慢日志同时记录总耗时和 pipeline 耗时。
- **验证**：30 分钟复现里两个慢请求分别为 30,352ms / pipeline 2.2ms、30,268ms / pipeline 0.5ms；后来补全 body/queue/persist/post 分段，剩余时间不在 `store.save`。
- **防复发**：延迟问题先加分段，再谈归因；总耗时不能定位到具体阶段。

## L011 · 没有 `_write` 慢日志不等于 commit 没问题

- **症状**：4 worker + batch 的 30s 请求，pipeline 只有 2.2ms；给 `RunWriter` 加 queue_wait/write_ms 后，20 分钟 4 个错误没有产生任何 >1s 的 `_write` 日志。
- **根因**：慢请求卡在写者线程开始执行之前（队列等待、线程调度或进程暂停），而不是 `save_rows`/commit 内部；之前的“写锁”假设过粗。
- **修复**：记录 `queue_wait_ms_max` / `write_ms_max` / `slow_events`，并在 `SHOTPLAN_WRITER_LOG` 写慢批次；下一步加入队 watchdog。
- **验证**：20 分钟 4 worker 的错误全部没有 writer 慢日志；同一批请求行仍全部落库。
- **防复发**：没有某一段的慢日志，只能证明“不在这段”，不能证明“就是下一段”；继续加观测点，不用猜测填空。

## L012 · 分段算平后，30s 不在任何应用段内

- **症状**：三个 30.3s 级慢请求，body/queue/pipeline/sink/persist/post 各段合计只有约 26–49ms，剩余约 30.2s 没有归属。
- **根因**：之前只测了 pipeline 和 persist，把“总时长减去已知段”直接归给下一个猜测（先是 SQLite，再是 writer 队列）；没有把端点前/ASGI 中间件也纳入分段。
- **修复**：响应头增加 `X-Body-Duration-Ms`、`X-Queue-Duration-Ms`、`X-Persist-Duration-Ms`、`X-Post-Duration-Ms`；慢日志同时记录全部段。
- **验证**：`docs/single-writer.md` 的分段总账；持久化、SQLite、writer 队列均被排除。
- **防复发**：总时长必须能被各段加平；加不平就继续加观测点，不能把差额归给下一个假设。
