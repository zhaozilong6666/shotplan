# 多轮追问：每个修复各值多少

2026-11-17。被测对象是 `followup.py` 的确定性规则，不调模型，所以这页的每个数字都可以原地复跑。

## 结论

| 配置 | dev（12 条） | holdout（12 条） |
| --- | ---: | ---: |
| 原版（`git show HEAD:` 的 `followup.py`） | 5 | 3 |
| 新版，关掉数字 / 风格 / 时刻 | 7 | 4 |
| 新版，只开数字 | **10** | **10** |
| 新版，全开 | **12** | **12** |

边际贡献（从全开里单独去掉一项，看损失几条）：

| 去掉 | dev | 损失 | holdout | 损失 |
| --- | ---: | ---: | ---: | ---: |
| 数字解析（`_apply_amounts`） | 9 | **−3** | 6 | **−6** |
| 风格替换（`_apply_styles`） | 11 | −1 | 11 | −1 |
| 结束时刻（`_apply_deadline`） | 11 | −1 | 11 | −1 |

可加性检验：`12 − 3 − 1 − 1 = 7`，正好等于「关掉三项」的实测值；holdout 上 `12 − 6 − 1 − 1 = 4` 也吻合。
**三个修复各自命中不同用例，没有互相掩盖**，所以上面每个数字都能单独引用。

## 三个发现

### 1. 我自己漏算了一块，第一次消融因此是错的

第一次做消融时，我以为「关掉数字 / 风格 / 时刻」就等于原版，跑出来 **7/12**。但原版是 **5/12**。
差的 2 条来自 `_apply_verbal`——重写时我顺手把它从「只认加向词」扩成了「加向 + 降向」，
这属于改动本身，不属于"原版行为"。

教训：**基线不能靠关掉几个函数来近似**。要拿原版数字，就去 `git show HEAD:` 取原文件跑一遍。
消融只能回答"这一项现在值多少"，不能回答"改动前是什么样"。

### 2. 数字解析是主项，但不是全部

dev 上 +3、holdout 上 +6。holdout 的差距更大，因为留出集里换了说法（「少 200」「砍到 1000」
「五个小时」「两千五」），全靠数字解析——原来的固定步长一条都过不了。

但它只到 10/12，剩下两条恰好是风格和时刻：**一个模块再强也补不上另一个字段的入口缺失**。

### 3. 时刻识别只值 1 条用例，但它是唯一改变"约束"性质的改动

M07 只贡献 1 条通过数，看起来性价比最低。但另外两项改的是"数值填得对不对"，
这一项改的是**方案的结束时间会不会被检查**：新增软规则 `END_AFTER_DEADLINE`，
让「17:00前结束」从一句写进 brief 的备注，变成校验器会读、修复循环会看见的条件。

这一点的诚实边界：软规则**没有在真实模型上验证过**是否会触发、修复循环能否改对。
规则本身的单元测试覆盖了"晚于承诺时刻会报"和"已经满足不报"，但"模型会不会排到 17:00 之后"
是另一个问题，需要真实模型实验，本轮没做。

## 复跑方式

```bash
# 原版基线
cp src/shotplan/followup.py /tmp/new.py
git show HEAD:src/shotplan/followup.py > src/shotplan/followup.py
py -3.12 -m evals.multi_turn_lab --holdout /nonexistent
py -3.12 -m evals.multi_turn_lab --cases evals/multi_turn/holdout.jsonl --holdout /nonexistent
cp /tmp/new.py src/shotplan/followup.py

# 边际贡献：把对应函数替换成 no-op 后跑同一套用例
```

第二个命令需要临时脚本（替换模块属性），本轮用的脚本在对话里，未入库——
因为它依赖内部函数名，随重构失效的风险高于它作为证据的价值。**结论可复跑，脚本不必长存。**

## 口径

- 一条用例通过 = `expect` 里每个字段都对，且最后一轮的「识别/拒答」符合预期。
- dev 与 holdout 是两批句子，写法不重叠；holdout 首跑 9/12，之后在它上面改过三次，
  因此 holdout 的 12/12 只能当回归结果，不是泛化证据。详见 [multi-turn.md](multi-turn.md)。
- 所有数字无采样、无并发、无网络，同一份代码在同一台机器上结果恒定。
