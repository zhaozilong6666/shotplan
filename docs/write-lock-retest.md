# 多 worker 同库写入复测

> 2026-11-20，E24。回应 [上线就绪度](release-readiness.md) 第 6 项。
> 吞吐只报告、不进 CI 门禁（ADR 0008）；门禁只断言「0 错误、0 丢写」。

## 结论

- **契约仍成立**：1 / 2 / 4 worker 各 200 请求，全部 0 错误、`persisted=200/200`。
- **吞吐与旧快照不一致**：4 worker 相对 1 worker 是 **2.61×**，不是旧报告里的 **0.52×**。
- **主要混杂是解释器**：旧快照在 Python **3.13.14** 下生成，本次是 **3.12.4**；同一台机器、18 逻辑核。
  两者不是同一环境，不能直接比较，也不能据此宣布「多 worker 更快」。
- 能确认的只有：在 3.12 上，多进程同写同一 SQLite 仍然**不丢写**。

## 与旧快照对照

| 场景 | 3.13.14（旧快照） | 3.12.4（本次） |
| --- | ---: | ---: |
| 1 worker 并发 8 | 250.66 /s | 47.97 /s |
| 2 worker 并发 8 | 280.37 /s（1.12×） | 93.51 /s（1.95×） |
| 4 worker 并发 8 | 129.62 /s（0.52×） | 125.42 /s（2.61×） |
| 错误 / 丢写 | 0 / 0 | 0 / 0 |

单 worker 差 5 倍、而 4 worker 绝对吞吐接近，说明这不是「代码变快/变慢」，
更像是 3.12 下单进程的请求路径更慢，于是多进程才有摊薄空间。**未做同解释器对照前，不下结论。**

## 为什么保留旧快照

`docs/http-load.md` 与 `evals/http_load.json` 仍是 3.13 生成的历史快照。没有用本次覆盖：

- 解释器不同，覆盖会把两个环境混成一条时间线；
- 吞吐是机器相关量，本来就不进门禁；
- 旧快照里的 0.52× 是一个真实测量，不应被另一个环境的数字抹掉。

需要更新对外数字时，应先在**目标部署解释器**上重跑 `--write`，再统一改文档。

## 下一步

1. 在目标解释器（当前部署是 3.13）建 venv、装依赖，重跑 `--write`，做同解释器对照；
2. 若 3.13 仍复现 0.52×，检查 3.12 下是哪一段变慢（SQLite 提交、JSON 序列化、asyncio）；
3. 上线 worker 数变化后，重复本复测；**丢写是契约，吞吐不是**。
