# 多 worker 同库写入复测

> 2026-11-20，E24。回应 [上线就绪度](release-readiness.md) 第 6 项。
> 吞吐只报告、不进 CI 门禁（ADR 0008）；门禁只断言「0 错误、0 丢写」。

## 结论

- **丢写契约成立**：1 / 2 / 4 worker 各 200 请求，两个解释器下 `persisted` 都等于成功请求数。
- **旧快照的 0.52× 不再复现**：v0.8.0 的 4 worker 回落（129.62 /s，0.52×）在当前提交上
  用 Python 3.12 和 3.13 各跑一遍，都变成正扩展（2.61× / 2.99×）。
- **单 worker 绝对吞吐低了一个量级**：旧快照 250.66 /s，现在 29–48 /s。变化不在多进程写锁
  一处，而是整条请求路径比 v0.8.0 慢；具体归因未做，不下结论。
- **复测撞到一个真实故障**：4 worker 冷启动时出现过 **1 个 503**（SQLite 建表竞争）。
  已给初始化加重试；修复后一轮 0 错误，但样本只有一轮，不能宣称彻底消除。

## 复测中撞到的 503：4 worker 建表竞争

在一次 4 worker 运行里出现：

```
HTTP 503: {"detail":"cannot initialise database at .../runs.db:
attempt to write a read-only database"}
```

成功请求仍全部落库（199/199），所以**没有丢写**；但 1 个请求直接失败。原因不是文件系统只读，
而是 4 个 worker 同时执行 `PRAGMA journal_mode=WAL` 与 `executescript(_SCHEMA)`，其中一个
在另一个持有创建锁时被 SQLite 判成 read-only。

修法：`RunStore._init` 对 `locked / readonly / read-only / busy` 三类瞬时错误重试 3 次
（50 / 100 / 150 ms），对「unable to open database file」这类永久错误不重试。
修复后先跑一轮 5 场景 0 错误；随后用 `startup_race_lab` 做了 **20 轮 × 4 worker 冷启动**
复测（E25）：**0 启动失败、0 个 503、0 丢写**，启动中位数 2.26s（[startup-race.md](startup-race.md)）。
这仍不能证明概率为零；`http_load --check` 只跑 1 worker，覆盖不到这个竞争。

## 为什么会出现吞吐差异

未做逐段归因，只能列候选：v0.8.0 之后加了持久化模式、请求预算、更多校验与 trace，
单请求成本上升；单 worker 变慢后，多进程才有摊薄空间。**这是解释，不是测量**。

## 下一步

1. 在目标部署解释器上把本复测作为基线，worker 数变化后重跑；
2. 若要解释单 worker 为什么慢了 5–7 倍，按阶段（HTTP/JSON、pipeline、SQLite 提交）做
   profile，而不是继续比较总吞吐；
3. 给 4 worker 冷启动竞争做一个多轮启动测试，确认重试是否真的消除 503；
4. **丢写是契约，吞吐不是**；任何吞吐结论都要带日期、解释器、机器与 `persist_mode`。
