## 方法

1. 每个用例是一段**模糊客户 brief**（时长、预算、风格、日期、排除项），不是固定输出 fixture。
2. 两个 provider 在**完全相同**的用例上各跑一遍；`naive` 故意忽略时间、转场、预算与溯源。
3. 每份输出都经过同一个**不依赖模型的硬约束校验器**，由它给出问题清单与分项得分。
4. 用例通过需同时满足：硬约束结论符合预期，且得分不低于该用例的分数下限。
5. 维度权重：`constraints 0.40 / budget 0.20 / traceability 0.15 / light 0.15 / completeness 0.10`。
6. 不可满足需求的用例单独计分：正确返回结构化拒绝记 1.0，硬凑一份违规方案记 0.0。

对照组的意义：如果只对自己写的 planner 跑评测，很容易写出一套永远通过的评分器。把一份明确不可执行的方案放进去，是检验评测本身是否有效的控制组。

## 测量有效性：对照组的规则覆盖

「对照组分数低」还不够。故意犯错的方案同时违反多条规则，少命中一条时它的 `constraints` 维度可能仍被 clamp 到 0，均分几乎不动——也就是说，**悄悄删掉一条硬规则，旧门禁可能照样全绿**。因此门禁还要求每条已知缺陷都必须被报出来（下限约为实测次数的一半，新增用例不会让下限漂移）。

## 不可满足需求识别

共 **11** 个用例的 brief 在数学上无法同时满足（预算低于最低可执行成本、时长过短、未知城市或约束互相矛盾）。
正确行为是**在生成之前停止并返回结构化原因 + 缺口 + 建议**，而不是硬凑一份会被校验器打回的方案。
本次正确识别并通过：**11/11**。

可行性判定不经过模型、且发生在生成之前，所以两个 provider 在这些用例上共享同一结论；两组之间的区分度由其余用例提供。这是「AI 系统里哪些判断不该交给 AI」的第二个例子（ADR 0007）。
