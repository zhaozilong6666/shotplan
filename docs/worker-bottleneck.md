# 对照实验：多 worker 变慢，真的是 SQLite 写锁吗

> 由 `python -m evals.worker_lab --write` 生成本机快照。数字机器相关，**不进 CI 门禁**。

## 为什么要做这个实验

[http-load.md](http-load.md)（v0.8.0）测到 4 个 uvicorn worker 比 1 个还慢，并把它归因于「多个进程抢同一个 SQLite 写锁」。那是**推断**，不是受控实验。
本项目一直要求「结论要能被证伪」，所以这里补上对照组。

做法：给服务加一个开关 `SHOTPLAN_PERSIST_RUNS=0`，让**同一份产品代码**在 `run_plan(..., store=None)` 下跳过运行历史写入；HTTP、ASGI、JSON 序列化、provider、校验、修复全部不变。其余唯一变量就是「有没有同步写 SQLite」。

环境：Python 3.13.14 / Windows / 18 逻辑核；并发固定 8，每个组合 200 次请求、重复 2 轮取**中位数**。开 / 关两组在同一批内交替跑，避免跨批机器负载漂移影响相对比较。

## 结论

**假设成立**。

- 关掉运行历史写入后，1 worker 吞吐变为 **2.48×**、2 worker 变为 **3.59×**：持久化确实是关键路径上最大的单项开销，这一条在本次所有轮次都稳定。
- 有写入组 4 worker 相对 1 worker 的**逐轮**比值是 0.86× / 0.92×（中位数 0.89×），关掉写入后是 **1.59×**；两组最佳点分别是 2 / 4 worker。
- 去掉写锁后 4 worker 不再回落：**在本次负载下**支持「共享 SQLite 写者争用是回落主因」这一归因。它是有条件的结论，不是普适规律（见边界一节）。

- 修正后的工程建议：想提吞吐，**第一杠杆是把运行历史写入移出同步关键路径**（异步写、批量写或独立写服务）；worker 数应实测找拐点，不是越多越好。运行历史本身是可观测性与回归追溯的基础，不该删掉，只该异步化。

## 与上一版报告的关系

- `docs/http-load.md` 的归因在本批数据下**得到支持**：关掉持久化后 4 worker 不再回落。但它仍是有条件的结论——另一批独立运行中「回落」本身没有稳定复现，因此不写成普适规律。
- 展示页、中英文 README、面试讲稿 Q&A 与 CHANGELOG 同步标注了这一层证据，并在 [ADR 0011](adr/0011-controlled-experiment-over-inference.md) 记录「先做对照实验再下因果结论」这条方法论。

## 门禁检查什么

`python -m evals.worker_lab --check` 只跑两个短场景（1 worker，开 / 关各 20 次请求），断言：

1. 两组都 0 错误、返回合法 `status=ok` 方案；
2. 持久化**开**时 `total_runs` 增量等于成功请求数；
3. 持久化**关**时 `total_runs` 增量恒为 **0**——证明开关真的改变了服务端行为，而不是实验自欺欺人。

吞吐、中位数、加速比与结论文字**都不进门禁**：它们随机器负载变化，沿用 [ADR 0008](adr/0008-fuzz-and-benchmark-gates.md) 的原则。

## 边界

- 单机 loopback、离线 provider、无 TLS / 反向代理 / 真实模型延迟。
- 样本仍偏小，本机两次运行的绝对值可差数倍；结论只看**同一批内的相对关系**。
- 同一台机器不同批次可能给出不同 verdict：另一次独立运行里，有写入组的 4 worker 反而比 1 worker 快 2.42×，「回落」根本没有出现。稳定复现的只有「同步写库是最大单项开销」；任何关于 worker 回落原因的因果说法，都需要更多重复与更严格的负载隔离后才能下。
- 「持久化是最大开销」不等于「应该永远关掉历史」：运行历史是可观测性与回归追溯的基础。正确做法是把写入异步化 / 批量化，而不是删掉。

## 复现

```bash
python -m evals.worker_lab --check   # CI 门禁
python -m evals.worker_lab --write  # 重跑完整矩阵并刷新报告
```
