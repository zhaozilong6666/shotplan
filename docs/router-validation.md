# prompt 路由的前瞻验证：没通过

结论：**`SHOTPLAN_PROMPT_ROUTER` 保持默认关闭，不建议启用。** 在没见过的新用例上，它带来的收益消失了。

## 为什么要专门做这一轮

`planner-v3` 在 12 条光线敏感用例上得分 +0.0431（95% CI [+0.0127, +0.0763]，区间不跨 0），于是有了「按 brief 特征把这类请求路由到 v3」的想法。

但那 12 条**既是挑出路由规则的数据，又是 v3 显出优势的数据**。用它们验收等于自己给自己出题，是典型的选择偏差。所以另造 16 条 holdout：8 条光线敏感 + 8 条普通，城市、日期、措辞、必去地点全部换新，且 id 与 `redteam_soft` 无一条重合。

离线先确认：16 条全部可行、规则 Agent 全部可解；路由在 8 条光线题上全部触发、8 条普通题上全部不触发。

## 结果

两臂同批 16 例、同模型、同温度、并发 2，各跑一轮，均零异常。

| 指标 | 路由关闭 | 路由开启 | 差值 (B−A) |
| --- | ---: | ---: | ---: |
| 硬约束通过率 | 100% | 100% | +0.0 pp |
| 平均得分 | 0.8779 | 0.8786 | **+0.0007** |
| 得分 95% CI | — | — | **[−0.0343, +0.0338]** |
| 光线组得分 | 0.8444 | 0.8469 | +0.0025 |
| 普通组得分 | 0.9114 | 0.9103 | −0.0011 |
| `LIGHT_MISUSE` 次数 | 7 | 8 | +1 |
| 有软问题的用例 | 43.8% | 50.0% | +6.3 pp |
| 成本 | ¥0.57 | ¥0.51 | −¥0.06 |

配对比较：**6 胜 2 负，区间跨 0，测不出差异**。

## 三条结论

**1. 收益没有迁移。**
调参集上 +0.0431，holdout 的光线组只剩 +0.0025，不到前者的 6%。整体 +0.0007 完全在噪声里。当初那个「区间不跨 0」是真的，但它只在那 12 条上成立。

**2. 不是因为 holdout 没戳到问题。**
两臂分别有 7/16 和 8/16 的用例触发 `LIGHT_MISUSE`，机制确实被激活了；v3 照样没帮上忙。所以这不是「题目太软测不出」，而是修复本身不稳定。

**3. 路由器至少没造成伤害。**
普通组得分 −0.0011，成本也没有系统性上升（这轮反而便宜 ¥0.06，属波动）。但「无害」不构成开启的理由——一个增加了系统分支、却没有可测收益的开关，只会让以后更难复现。

## 决策

- `SHOTPLAN_PROMPT_ROUTER` 保留在代码中但**默认关闭**，标注为「前瞻验证未通过」。
- 不再基于现有数据继续调路由关键词：那会在同一批数据上反复过拟合。
- 若还想救 v3，应该先弄清 `LIGHT_MISUSE` 的成因（模型自选开始时间、偏好词被忽略），改的是**知识/约束**而不是再换一版 prompt 措辞。

## 局限

- 单轮、单模型、单供应商；16 例配对只能检测约 0.06 的得分差异，+0.0431 那种量级本来就在边缘。
- 两臂的 `LIGHT_MISUSE` 按全局统计，未能逐例定位到某个分组（快照未保存逐例问题码）。
- 成本差 ¥0.06 是单次采样，不能当成「v3 更便宜」的证据。

## 复现

```bash
SHOTPLAN_PROMPT_ROUTER=0 python -m evals.real_model_lab --cases-dir evals/router_holdout \
  --write --out evals/router-holdout-off.json --report-path docs/router-holdout-off.md
SHOTPLAN_PROMPT_ROUTER=1 python -m evals.real_model_lab --cases-dir evals/router_holdout \
  --write --out evals/router-holdout-on.json --report-path docs/router-holdout-on.md
python -m evals.pair_compare --a evals/router-holdout-off.json --b evals/router-holdout-on.json
```
