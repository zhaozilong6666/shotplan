# 面试笔记

## 30 秒版

> 我做了一个旅拍方案 Agent。核心不是调模型，而是先把「一份能执行的方案」写成 12 条可测试的硬约束——时间不重叠、妆造在拍摄之前、跨景点留足转场、预算不超、地点必须真实存在。生成之前先判断需求在数学上可不可满足，不可满足就直接结构化拒绝；生成之后模型输出再过这层确定性校验，校验报告转成修复提示回喂，并且只有新方案严格更优才替换。为了让质量可比较，我建了 80 个用例、覆盖五座城市的评测集和一个故意犯错的对照 provider。最想讲的是我没停在 80/80 全绿：我给门禁本身做了变异测试，注入 8 处受控故障，发现旧门禁漏掉 4 处「悄悄删掉一条校验规则」的改动，补齐对照组规则覆盖后 8/8 全部拦截。我也没停在「只有一套手写用例」：从失败案例库挖出 200 个主集没见过的组合做盲测，独立存放不污染基线；最后把服务真正跑起来压测，发现多 worker 反而变慢；我没有停在「听起来合理的解释」，而是加了个开关做开/关对照，还让实验可以判「不确定」。除了「对不对」，「崩不崩」「慢不慢」「并发丢不丢写」「尺子准不准」都做成了门禁。

## 10 分钟讲法顺序

1. **问题**（1 分钟）：LLM 生成的计划看起来很美但不可执行——一天排五个外景、景点名是编的、妆造排在拍摄之后。
2. **定义**（2 分钟）：什么算可执行？把约束分成硬/软，现场跑 `python -m shotplan.cli rules`。强调「判定不交给模型」。
3. **架构**（2 分钟）：画「可行性判定 → 检索 → 生成 → 解析 → 校验 → 修复」流程图，指出信任边界在 `planner.py`，并说明前判定与后校验是两处独立的「不交给 AI」判断点。
4. **质量证明**（2 分钟）：展示评测报告里 good **0.9788** / naive **0.3014** 的对照、80 个用例四组分布（normal 30 / conflict 23 / edge 16 / infeasible 11），解释为什么必须有控制组，以及「正确拒绝」为什么记满分；再补一句「80/80 只说明见过的题会做」，引出盲测挑战集。
5. **不止评测**（2 分钟）：另外八层证据——模糊测试（1000 个垃圾输入 0 崩溃）、性能基准（p95 0.4ms 量级）、并发负载（600 次请求 0 错误 0 丢写）、线程 vs 进程（线程 1.04× vs 进程 1.72×，瓶颈是 GIL）、**门禁有效性变异测试**（8 处注入、旧门禁漏 4 处）、**盲测挑战集**（225 候选 → 200 个未见 brief，城市 × 风格覆盖 19/25 → 25/25）、**真实 HTTP 压测**（1/2/4 uvicorn worker，1000 次请求 0 错误 0 丢写）、**持久化对照实验**（关掉同步写库后 1 worker 提速 2.48×，验证写锁归因且允许判「不确定」）。挑一条讲深：压测抓到的 SQLite 并发缺陷，或变异测试暴露的「对照组太烂导致单条规则失效不可见」。
6. **诚实边界**（1 分钟）：知识库是静态小样本、离线 provider 是当前规则的上限参考、成本/延迟在离线模式是模拟值、没有真实部署与真实模型数据。主动说限制比被问出来好。

| | 内容 |
| --- | --- |
| **S 情境** | 旅拍工作室的排期是人工做的：一个 brief 进来，要判断预算够不够、光线窗口够不够、妆造和转场排不排得下。用 LLM 直接生成，输出看着漂亮但不可执行——一天排五个外景、景点名是编的、妆造排在拍摄之后。而且「哪一版更好」只能靠人看，改一次 prompt 就不知道是变好还是变差。 |

## 三个最尖锐的问题

**Q：你这个东西严格说不是 Agent，是一条 pipeline。为什么要叫 Agent？**

先承认：它不是自主 agent。系统里没有「模型决定下一步调哪个工具」这一层——知识在生成前一次性取好，生成是单次 JSON 输出，控制流全在代码里。我按「能自主编排工具」的标准衡量，它不合格。

但我认为这个取舍是对的，理由不是「做不出来」，而是「做了会更差」：这个产品的失败模式是**方案不可执行**，不是**步骤不够多**。多轮 tool calling 会引入一个新的不确定性来源（模型选错工具、参数漂移），却不会让硬约束校验更可信——校验本来就不经过模型。所以我宁愿把这部分复杂度预算花在「判定是否可信」上：12 条规则、对照组、变异测试、盲测集。

什么情况下我会加循环？当「下一步查什么」无法预先确定时。比如真实商家档期：要先查档期、再按空档重排、档期变了要回退——那时工具调用是有信息增益的，我会加，并且会给它加上重试上限和墙钟预算（预算这条现在已经有：超时带着最优草稿降级返回，不是无限等）。

**Q：你说解析器能自动修复模型输出，那会不会把错的数据悄悄放进来？**

会，所以修复分两类，边界写死在代码里：

- **无歧义的结构问题**才修：markdown 围栏、JSON 前后的说明文字、同一个 payload 里有多个对象（取第一个能真正构建出方案的）、末尾多余逗号、全角引号。这些修完语义不变，而且**每一次修复都写进 trace 的 `notes`**，`/api/config` 和运行详情里能看到「这次是修过的」。不是静默吞掉。
- **数字绝不猜**：`cost_cny: "免费"` 认作 0（有明确的免费标记），`"¥300"` 认作 300，但 `"大约三百"` 直接 `ParseError`。把读不出的价格当成 0 是最坏的失败方式——预算规则会对一个严重超支的方案判通过。

这条边界是被一个真 bug 逼出来的：原来 `int(item.get("cost_cny") or 0)` 遇到中文会抛 `ValueError`，而流水线只 catch `ShotplanError`，于是模型返回一个「免费」就让接口 500。现在整个解析层是一个信任边界，任何异常都收敛成 `ParseError` → `status=error` 的结构化失败，并且有一条 300 次变异的确定性测试守着「只允许抛 ParseError」。

**Q：异步化既然快 3 倍（另一批量到 5.5 倍），为什么默认不开？**

因为默认值是一句承诺，不是一个性能参数。项目在并发测试里对外写过「每个被接受的请求都已落库」，所有并发门禁也按这条断言。异步模式改变的是这条承诺的边界：进程被 SIGKILL 或断电时，队列里还没提交的行会丢。

我没有把这句话写成「理论上可能丢」，而是去量它：起一个子进程，写入 N 条，然后 `os._exit(0)` 跳过所有清理，父进程数库里的行。先 flush 再退出的变体读到 N 条；不 flush 直接退出的变体读到 N−pending 条，且 `pending` 和差值一致。所以这是一个**有界、可数、可监控**的窗口（队列深度 × 批次间隔），而不是一个黑洞。队列满时也不丢行，退化为同步写并计数。

那为什么还要留着 `sync` 当默认？因为收益的承受者（部署方）和承诺的承受者（调用方）不是同一个人。我把 `async` 做成一行环境变量就能开，把收益、代价、丢失窗口和复现命令都写在 [persistence.md](persistence.md) 里，让选择发生在知情的前提下——而不是我替他选，然后继续用原来的宣传口径。

- 把上一轮实验留下的建议真正实现并验证：为运行历史加写后置队列（进程内单写线程 + 批量事务 + 队列满退化同步写），`off/sync/async` 三组同批对照显示异步相对同步 1 worker **2.96×**、4 worker **1.95×**，拿回约 47% 写库开销，P95 186ms → 93ms，三组 0 丢写；默认仍保持 `sync`，异步的持久性边界用子进程 `os._exit` 真杀测量而非推断（ADR 0012）。
- 把流水线从「顺序代码 + 手绘图」改成可校验的契约：6 个节点写成 `STAGES` 表，Mermaid 图与逐节点输入/输出由代码生成、CI 比对漂移，测试断言运行时 trace 事件全部来自这张表；新增墙钟预算，超预算时带着当前最优草稿降级返回而不是丢弃或无限重试（ADR 0013）。
- 修掉信任边界上的一个真实缺陷：解析层用 `find/rfind` 定位 JSON，字符串里含 `}` 或 JSON 后带说明文字就会切错；`int("免费")` 抛出的 `ValueError` 会绕过只处理 `ShotplanError` 的编排层变成 HTTP 500。改为括号配平扫描 + 显式降级修复（每次修复记入 trace）+ 数字绝不猜，补 300 次确定性变异测试守住「只允许抛 ParseError」。
- 压测发现并修复两处并发缺陷：SQLite 每次请求重建连接导致建表/WAL 初始化抢锁（偶发 422）、rollback journal 的 fsync 让写者互斥；改用 WAL + 进程级初始化/写锁 + 有限重试后，并发 8 的 p95 从约 200ms 降到约 27ms，吞吐约 100/s → 约 310/s。

## 高频深挖问答

**Q：为什么不用 LLM-as-judge？**
判定标准会随模型和 prompt 漂移，而且模型不擅长发现自己刚犯的时序/算术错误。把判定放在确定性代码里，跨模型、跨版本的分数才可比较，也才能写单元测试。主观审美那部分明确没有纳入评分，写在已知限制里。

**Q：可行性判定为什么也不交给模型？**
「350 元够不够做一次拍摄」「1.5 小时排不排得下妆造+转场+拍摄」是纯算术与约束可满足性问题，模型既不稳定也没必要参与。放在生成之前还能省掉一次无意义的生成与修复（真实模型下省 token 和延迟）。这和校验器不经过模型是同一个原则：要能说清哪些判断必须由确定性代码负责。

**Q：怎么防止模型编造地点？**
所有 `location_id` 必须在知识库白名单中。解析层是信任边界，校验层再做一次白名单检查；命中即硬失败，并把 `UNKNOWN_LOCATION` 与建议写进修复提示。

**Q：修复循环会不会越改越差？**
会，所以做了单调保护：只有 `(hard_pass, score)` 字典序严格变大才接受新草稿，否则保留原方案。我用三个刻意构造的 provider 做了对照实验：会读报告的 provider 一次修复成功率 69/69；忽略报告的 69 次候选全被拒；「越修越差」的 69 次全被单调保护拦下。每次接受/拒绝都从 trace 的 `accepted` 字段读，不靠推断。

**Q：0.98 分是不是太完美了，评测有意义吗？**
当前离线 provider 是照着规则写的，高分在预期内，它是上限参考。评测体系当下的价值由对照组证明：naive 只有 0.3014（其中 11 个不可满足用例因共享前置判定而正确拒绝），说明打分器确实分得出好坏。真正的压力测试在接入真实模型之后。我不会把 0.98 说成「系统效果好」。

**Q：为什么还要做模糊测试？评测集不够吗？**
评测集回答「在真实 brief 上够不够好」，回答不了「乱传参数会不会崩」。请求是从 JSON 直接进领域模型的，中间没有 schema 层，所以 `hours="abc"`、`budget_cny=None`、`styles` 传字典、`NaN`、`1e400` 都能到达模型层——以前这些会让 API 返回 500。我把归一化改成全域函数、非法日期走 `DATE_INVALID` 预检、provider 或解析失败返回 `status=error`，再用 1000 个变异输入守住这条契约。每个用例带种子，失败可单条复现。

**Q：并发上你踩过什么坑？**
两个，都是压测才暴露的。第一，API 每个请求都新建 `RunStore`，多线程同时 `CREATE TABLE` + `PRAGMA journal_mode=WAL` 互相抢锁，约 2/80 请求返回 422（`attempt to write a readonly database`）。第二，默认 rollback journal 每次提交都 fsync，写者互斥，并发 8 的 p95 高达 180–230ms、吞吐比单线程还低。改成 WAL + 进程级初始化锁/写锁 + 对 locked/readonly 有限重试后，p95 约 27ms、吞吐约 310/s，600 次请求 0 错误 0 丢写。这两条都写进了 `docs/loadtest.md`。

**Q：既然进程池能到 1.72×，真实服务里加 worker 为什么反而变慢？**
两个实验负载不同：进程池跑纯函数、worker 不共享状态；真实服务每个请求都要写一条运行记录。但我不会停在「所以是 SQLite 写锁」这种推断上。v0.9.0 我给同一份产品代码加了 `SHOTPLAN_PERSIST_RUNS` 开关，只改变「要不要同步写库」，在同一批内交替跑 1/2/4 worker × 开/关 × 2 轮取中位数。关掉写库后 1 worker 吞吐提升 2.48×、2 worker 3.59×；有写入组 4w/1w 逐轮 0.86 / 0.92，关掉后变成 1.59×，本批数据支持写锁归因。

更有意思的是判定逻辑：它先检查「回落现象本身是否逐轮复现」，允许输出 `inconclusive`。另一批独立运行里 4 worker 反而比 1 worker 快 2.42×，回落根本没出现。所以稳定复现的只有「同步写库是最大单项开销」，写锁归因只是有条件的定性结论。报告里「与上一版报告的关系」随判定动态生成，不写死结论；吞吐依旧不进 CI，门禁只验证开关真的生效（开 = 全落库、关 = 0 落库）。

**Q：为什么加进程而不是加线程？**
有数据：同一 workload 下线程最好 1.04×（GIL 限制），进程最好 1.72×（18 逻辑核的机器）。所以部署层应该加 worker 进程（`uvicorn --workers N`），而不是加线程。代价是每进程内存与启动开销，所以也不是越多越好。

**Q：你怎么证明 CI 的门禁不是摆设？**  
80/80 全绿只能说明当前代码通过了当前检查。我在进程内注入 8 处受控故障（不插转场、转场费抬 100 倍、删妆造块、放宽预算、放宽时长、白名单失效、校验器直接返回满分……），跑同一套用例，要求真实门禁全部拒绝，再回滚逐字段比对。结果旧门禁只拦住 4/8：漏掉的全是「校验端被悄悄削弱」——对照组方案太烂，少一条硬问题均分几乎不动，好方案更是完全不变。于是加了对照组规则覆盖下限：每条已知缺陷必须被报出来，再加差值下限与对照组上限，现在 8/8 拦截、0 存活。关键是实验室调用的是 `run_eval` 用的同一个门禁函数，不是复制一份阈值，测试里用对象身份断言锁住这一点。

**Q：为什么不把挖掘出来的用例直接补进主评测集？**
因为 `v1..v6` 六个时代的基线快照靠「主集变动缓慢且可解释」才可比较。批量塞进几百个自动生成的用例后，分数变化就分不清是「实现变好了」还是「题目变简单了」，连对照组规则命中下限、修复实验的 69 个 brief 都要重新解释。所以主集管纵向回归、挑战集管横向泛化，两者跑同一条流水线但职责分开；挖掘器也刻意不读取任何用例的期望输出，避免「照着答案写题」。`--check` 会重新挖掘并逐字节比对产物，改了校验器却没重刷挑战集会直接失败。

**Q：CI 里为什么特意跑四个 Python 版本？**
第一次推送就抓到真问题：Python 3.12 改了 `sum()` 的补偿求和行为，同一份满分方案在 3.10/3.11 算出 `1.0000000000000002`。我把评分改成 `math.fsum` + 固定 6 位精度，加了契约测试和 ADR 0006。评分要进报告、进基线、进门禁，不能随解释器漂移。

**Q：预算超支怎么算的？为什么不信任模型给的总计？**
取 `max(声明的 total_cost_cny, 所有时间块成本之和)`。模型可能在每个块填真实价格、汇总字段却低报，只信声明值等于留了个绕过约束的口子。紧预算下 planner 还会按剩余预算裁剪地点组合，并自动降级妆造档位——这是 C24 用例逼出来的实现修复。

**Q：为什么核心不用 pydantic / FastAPI？**
为了让 clone 后零凭证可跑，也为了让规则语义完全由自己代码定义。框架校验放在 API 边界。代价是要自己写归一化与 JSON 容错，这些集中在 `domain/models.py` 和 `planner.py`。

**Q：这个项目有什么没做到的？**
静态小样本知识库、没有实时票价客流、可行性下限是理论值而非商家报价、真实模型的成本/延迟对比尚未实测、没有真实部署（并发与扩展性是单机数据，不是生产 QPS）、没有鉴权与多租户；8 处变异是人为挑选的，只证明这几类回归会被发现；200 个盲测 brief 来自固定网格，代表组合多样性而不是真实客户分布；真实 HTTP 压测是单机 loopback 小样本，无 TLS / 反向代理 / 真实模型延迟，两次运行能差近一倍，不是生产 QPS；对照实验里「4 worker 回落」在另一批运行中没复现，所以因果结论是有条件的。都写在 README 已知限制里。

**Q：如果再做一个月，你会做什么？**
接真实模型跑 prompt v1/v2 对比实验，把实测差异写回 `PROMPT_CHANGELOG`；用真实模型的错误分布替换失败案例库里的对照组样本；把当前的单机数据换成容器内的真实 QPS；再补一层人工标注，检验自动评分与人的判断是否一致。路线图里每条都有验收标准。

## 别这么说

- 不要说「用了 AI 自动生成方案」——太泛，谁都能说。
- 不要吹 star 数；也不要只说「高并发」——直接给数字：线程 1.04×、进程 1.72×、并发 8 的 p95 约 27ms，并说明这是单机数据。
- 不要把 `naive` 对照组藏起来；它是方法论的一部分，主动讲会加分。
- 不要把离线 0.98 说成「模型效果好」，也别把「正确拒绝」用例两组同分说成评测失效。
- 不要把盲测挑战集说成「模型效果验证」：它只证明判定链在未见组合上一致，没有接入真实模型。
- 不要声称「压测过生产」——我只做了单机并发与进程扩展性实验，边界说清楚反而可信。
