# 面试笔记

## 30 秒版

> 我做了一个旅拍方案 Agent。核心不是调模型，而是先把「一份能执行的方案」写成 12 条可测试的硬约束——时间不重叠、妆造在拍摄之前、跨景点留足转场、预算不超、地点必须真实存在。模型输出先过这层确定性校验，校验报告再转成修复提示回喂，并且只有新方案严格更优才替换。为了让质量可比较，我建了 12 个评测用例和一个故意犯错的对照 provider，CI 里如果对照组分数追上正式方案就直接失败。

## 10 分钟讲法顺序

1. **问题**（1 分钟）：LLM 生成的计划看起来很美但不可执行，举一个真实错误例子——一天排五个外景、景点名是编的。
2. **定义**（2 分钟）：什么算可执行？把约束分成硬/软，展示 `python -m shotplan.cli rules`。强调「判定不交给模型」。
3. **架构**（2 分钟）：画检索 → 生成 → 解析 → 校验 → 修复的流程图，指出信任边界在 `planner.py`。
4. **质量证明**（2 分钟）：展示评测报告里 good 0.9734 / naive 0.19 的对照，解释为什么需要控制组。
5. **工程细节**（2 分钟）：trace、SQLite 留痕、零依赖核心、修复循环单调不降、CI 阈值。
6. **诚实边界**（1 分钟）：知识库是静态小样本、离线 provider 是当前规则的上限参考、真实模型接入才是压力测试。主动说出限制比被问出来好。

## 简历 bullets（挑 2–3 条）

- 设计并实现带确定性硬约束校验的旅拍方案 Agent：将时间冲突、转场不足、预算超支、地点幻觉等 12 条规则独立成可测试层，校验报告驱动定向修复，且拒绝接受质量下降的重生成结果。
- 搭建可复现的评测体系：12 个场景用例 + 故意犯错的对照 provider + 自动生成的回归报告，CI 以平均分与硬约束通过率为门禁，对照组有效性也被纳入检查。
- 核心引擎零第三方依赖（标准库实现配置、HTTP 重试、SQLite 留痕、JSON 容错），FastAPI 与前端作为可选层，保证无 API key 环境下完整可运行；76 个单元测试覆盖全部规则与边界。

## 高频深挖问答

**Q：为什么不用 LLM-as-judge？**
判定标准会随模型和 prompt 漂移，而且模型不擅长发现自己刚犯的时序/算术错误。把判定放在确定性代码里，跨模型、跨版本的分数才可比较，也才能写单元测试。主观审美那部分我明确没有纳入评分，写在已知限制里。

**Q：怎么防止模型编造地点？**
所有 `location_id` 必须在知识库白名单中，travel 块只允许 `-` 占位。解析层是信任边界，校验层再做一次白名单检查；命中即硬失败，并把 `UNKNOWN_LOCATION` 与建议写进修复提示。

**Q：修复循环会不会越改越差？**
会，所以做了单调保护：只有 `(hard_pass, score)` 字典序严格变大才接受新草稿，否则保留原方案。trace 里记录每轮的硬问题数量变化，可以统计「修复反而变差被拦截」的次数。

**Q：为什么不用向量数据库？**
知识库只有十几条，且约束是精确的（室内/收费/排除项/标签），相似度检索反而会漏。精确匹配还能给每条知识稳定 id，直接支撑引用溯源。规模到几千条时再重新评估，那条决策写在 ADR 0003。

**Q：评分权重怎么定的？为什么 constraints 占 0.40？**
可执行性是门槛而非加分项，所以单独用 `hard_pass` 做布尔门禁，评分里再给最高权重，让「勉强通过但一堆软问题」和干净方案拉开差距。每个权重的理由写在 `docs/problem-and-metrics.md`，权重总和由单测强制检查。

**Q：0.97 分是不是太完美了，评测有意义吗？**
这是好问题。当前离线 provider 是照着规则写的，高分在预期内，它是上限参考。评测体系当下的价值由对照组证明：naive 只有 0.19，说明打分器确实分得出好坏。真正的压力测试在接入真实模型之后，这也是路线图阶段 4 的核心任务。我不会把 0.97 说成「系统效果好」。

**Q：预算超支怎么算的？为什么不信任模型给的总计？**
取 `max(声明的 total_cost_cny, 所有时间块成本之和)`。模型可能在每个块填真实价格、汇总字段却低报，只信声明值等于留了个绕过约束的口子。

**Q：为什么核心不用 pydantic / FastAPI？**
为了让 clone 后零凭证可跑，也为了让规则语义完全由自己代码定义。框架校验放在 API 边界。代价是要自己写 JSON 容错和重试，这些集中在 `planner.py` 和 provider 里。

**Q：这个项目有什么没做到的？**
静态小样本知识库、没有实时票价客流、没处理「预算低于最低成本」的不可满足需求、没有用户鉴权和并发写入、没有人工标注的主观质量评分。都写在 README 已知限制里。

**Q：如果再做一个月，你会做什么？**
接真实模型跑 prompt 版本对比实验，把典型错误沉淀成新规则和用例；实现 `INFEASIBLE` 显式分支；做成本/延迟对比报告。路线图里每条都有验收标准。

## 别这么说

- 不要说「用了 AI 自动生成方案」——太泛，谁都能说。
- 不要吹 star 数、不要说「高可用高并发」，单进程 SQLite 撑不起这个说法。
- 不要把 `naive` 对照组藏起来；它是方法论的一部分，主动讲会加分。
