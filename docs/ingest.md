# 数据接入：把「手抄票价」变成可复核的管线

> `python scripts/ingest_city.py check` 是巡检；`fetch` 是单页提取。
> 只依赖标准库（`urllib` + `html.parser` + `re`），不引入解析库。

## 为什么要有它

这个仓库最脆的一环不是规划器，是知识库：**68 个地点的票价和开放时间全是手抄的**，
过两个月没人知道哪条过期了，也没有任何机制能发现。

加第 9 座城市也不会变好——只会让不可复核的面积更大。所以先修这一点：
把「查页面、抄数字」的机械部分交给脚本，只把判断留给的人。

## 它做什么

| 步骤 | 脚本做的事 | 人做的事 |
| --- | --- | --- |
| 抓取 | `urllib` + UA + 20s 超时 + 2MB 上限 | 给出正确的官方页面 URL |
| 转文本 | `HTMLParser` 去掉 `script/style` | — |
| 提取 | 票价、开放时间、停止入馆、闭馆日、预约天数 | 判断哪个是旺季价/成人价 |
| 对比 | 与 `locations.json` 现有值逐一比对，标出 `DIFF` | 决定改数据还是改页面 |
| 落库 | **不自动写入** | 人工确认后合入 |

## 用法

```bash
# 单页提取，先看看这个页面能不能读
python scripts/ingest_city.py fetch --url https://www.wuhouci.net.cn/

# 巡检所有已登记页面，与知识库对比
python scripts/ingest_city.py check --out drafts/ingest-2026-11.json
```

登记的页面在 `src/shotplan/knowledge/data/sources.json`：

```json
{ "chengdu/wuhouci": { "url": "https://www.wuhouci.net.cn/" } }
```

键是 `城市/地点id`，脚本会校验它确实存在于知识库里（防止登记幽灵条目）。

## 提取是保守的：缺失优于错误

知识库里一个错的票价，比一个查不到的票价更坏——它会被当真，并且没人再查。
所以规则只在页面**明确陈述**时取值：

- `全价门票 ￥50 /人` → `50`；页面只写「见购票页」→ **不写价格**
- `免费开放日的公告` → **不算 0 元**（那是公告标题，不是票价）
- `服务时间：08:00–20:00` → **不算开放时间**（那是客服电话的值班时间）
- `08:30 开放入馆 15:30 停止入馆 16:30 闭馆` → `08:30-16:30` + `last_entry: 15:30`
  （中间夹着另一个时间，规则必须允许跨越它，但不能跨越句子）

这三条都是被真实页面打过脸之后改出来的，测试里留了对应的反例（`tests/test_ingest.py`）。

## 已实测的覆盖

2026-11-16 用两个真实官网验证：

| 地点 | 知识库 | 网页提取 | 结果 |
| --- | ---: | --- | --- |
| 成都 / 武侯祠 | 50 | `50`、`09:00-18:00` | 一致 |
| 北京 / 故宫 | 60 | 票价未披露、`08:30-16:30`、周一闭馆 | 票价未知（正确），时间与闭馆日补全 |

故宫官网首页**不公布票价**（只有购票入口），所以脚本正确地报告「未知」而不是猜 60。
这正是这套设计想要的行为。

## 已知限制

- **单页只覆盖一个景点。** 一座城市 8–9 个地点就是 8–9 个 URL，脚本不负责发现页面。
- 官网常常不写票价（故宫就是这样），只能退化为「人工确认 + 脚本只核对开放时间」。
- 聚合站（携程/同程）多为 JS 渲染，直接抓取拿不到正文；本脚本不处理这种情况。
- 不解决「旺季/淡季两套价」。脚本给出的是页面上出现的那一个价，标注季节是人判断。

## 下一步（还没做）

1. 把提取到的 `open_time` / `closed_days` 变成**契约字段**，让规划器知道
   「故宫 16:00 停止入馆」，而不是把它只写在 `notes` 里。
   现在这是一个真实的产品缺陷：方案可能排出 16:00 进故宫的行程。
2. 多页聚合：一个 city manifest 描述 8 个 URL，一次抓完并输出草案。
3. 定期跑 `check`（例如每周），把 `DIFF` 写进 issue，而不是等人想起来。
