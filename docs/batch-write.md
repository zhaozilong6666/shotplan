# 批量提交：一次 commit，N 个请求都等到落库

并发 8、200 请求；同一份 mock 代码只改 `SHOTPLAN_PERSIST_MODE`，分别跑 1 / 4 worker。

## 结果

### 1 worker

| 模式 | 吞吐 (/s) | P95 (ms) | 错误 | 落库 | 丢写 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `sync` | 60.34 | 138.58 | 0 | 200/200 | 0 |
| `async` | 293.31 | 30.6 | 0 | 200/200 | 0 |
| `batch` | 195.68 | 54.32 | 0 | 200/200 | 0 |

`batch` 相对 `sync`：**3.24×** 吞吐，P95 为 sync 的 **0.39×**，丢写 0。

### 4 worker

| 模式 | 吞吐 (/s) | P95 (ms) | 错误 | 落库 | 丢写 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `sync` | 170.1 | 138.09 | 0 | 200/200 | 0 |
| `async` | 566.85 | 25.54 | 0 | 200/200 | 0 |
| `batch` | 228.03 | 69.18 | 0 | 200/200 | 0 |

`batch` 相对 `sync`：**1.34×** 吞吐，P95 为 sync 的 **0.50×**，丢写 0。

## 结论

- 1 worker：batch **3.24×** sync，P95 **0.39×**，丢写 **0**。
- 4 worker：batch **1.34×** sync，P95 **0.50×**，丢写 **0**。

## 语义

- `sync`：每个请求一次 commit，返回即落库。
- `async`：入队即返回，硬杀会丢队列里的行（已有测量）。
- `batch`：入队后**等一次共享 commit** 再返回；并发越高，摊薄越明显。队列满/关闭时退化为同步写，仍然等到落库。

## 边界

单请求、并发 1 时 batch 没有可合并对象，延迟与 sync 接近甚至略高；它是给并发服务的，不是给单请求提速的。吞吐数字机器相关，不进 CI 门禁。
