# 成本：钱花在哪，怎么降

结论：**九成成本付在输出 token 上，不在上下文。** 所以降本要压“模型说多少”，而不是拼命裁剪 prompt。

## 一、先看实测账单

最近一次干净的 80 例全量（`evals/real-model.json`）：

| 指标 | 数值 |
| --- | ---: |
| 输入 token | 140,573 |
| 输出 token | 463,325 |
| 每例平均输入 / 输出 | 1,757 / 5,791 |
| 单例 P50 延迟 | 44.3s |

一份 5 个时间块的 JSON 方案大约 700–900 token，也就是说**每次调用有约 5,000 token 是模型在“思考”，我们并不读**。按常见定价（输出单价约为输入的 4 倍）估算，输出占账单约 93%。

这也解释了为什么“优化 prompt 长度”几乎没用：把 1,700 的输入砍掉一半，账单只降 3%。

## 二、三个杠杆（已实现，默认关闭）

| 变量 | 作用 | 风险 |
| --- | --- | --- |
| `SHOTPLAN_LLM_MAX_TOKENS` | 给输出设上限，直接砍掉多余推理 | 截断会导致 JSON 不完整 → 解析失败；必须同时看通过率 |
| `SHOTPLAN_LLM_REASONING_EFFORT` | 传 `low`/`medium`/`high`，让推理型模型少想 | 不是所有端点都支持；不支持时会被自动丢弃并重试一次 |
| `SHOTPLAN_LLM_TEMPERATURE` | 默认 0.2；设为 0 可提升确定性 | 只降低波动，不直接省钱，但能减少“需要重复几轮才敢下结论”的轮数 |

三个值都会写进 `trace.config`，所以事后能回答“这次分数是用什么成本设置跑出来的”。

**重要**：`max_tokens` 不是免费的午餐。截断会让 JSON 解析失败，通过率可能下降。正确做法是把它当成一个实验变量，同时测「成本」与「通过率」，而不是先设一个便宜值再宣布胜利。这两种设置目前**尚未实测**（账户余额耗尽），不要先写进结论。

## 四、两个已落地的算法

**1. 自适应输出预算（`SHOTPLAN_LLM_ADAPTIVE_BUDGET=1`）**

不去猜一个固定上限，而是按方案规模估：

```
预算 = 520 + 300 × 预期时间块数      （预期块数 ≈ hours / 1.5 + 2，夹在 4–8）
```

请求时带上这个 `max_tokens`，然后看 `finish_reason`：

| 情况 | 动作 |
| --- | --- |
| `stop` | 直接用，**这就是省下的部分** |
| `length`（被截断） | 升到 2 倍重试一次 |
| 又被截断 | 第三次不带上限，保证能出结果 |

最坏情况多一次调用，常见情况每次省下几千输出 token。收益与风险都可以事后核验：`GenerationResult.metadata` 里有 `output_budget` 和 `truncated_retries`。

**实测（2026-11-14，8 例 smoke，`deepseek-v4.1-flash-261017`）**：

| 指标 | 开启前 | 开启后 |
| --- | ---: | ---: |
| 每例输出 token | 5,791 | **2,617** |
| 降幅 | — | **55%** |
| 8 例成本（估算） | — | ¥0.51 |

输出砍掉一半以上，且这一轮没有出现因截断导致的解析失败——但 8 例样本太小，不能据此宣布“零风险”。全量结果见 `docs/real-model.md` 的异常分布表。

**2. 分层抽样（`--limit` 默认 `--sample stratified`）**

这条是修 bug，不是优化。用例文件按 group 排列，`cases[:30]` 取到的是 **23 个 conflict + 7 个 edge、零个 normal**——小样本测的是另一批题，数字看着像结论，其实是另一个总体。

现在按 `group × city` 的 22 个分层做最大余数分配，固定种子、结果可复现，`sampled_case_ids` 写进快照。**30 例起才能覆盖全部 22 层**；8 例的 smoke 只用于判断“有没有整体崩”，不能代表通过率。

## 五、更省钱的是“少跑”，不是“跑得便宜”

| 策略 | 做法 | 省多少 |
| --- | --- | --- |
| 分档跑 | `--profile smoke`（8×1）/ `iterate`（30×1）/ `full`（80×3） | 冒烟约是全量的 1/30 |
| 改代码用 mock | 逻辑、校验、存储改动根本不调模型 | 100% |
| 只重渲染 | `--render` 用已有快照重出报告，不重跑 | 100% |
| 配对设计 | 同一批用例 A/B，样本需求减半（见 [measurement.md](measurement.md)） | ~50% |
| 熔断 | `--max-error-rate` 超阈值立即停，不写快照 | 避免“断供跑满全场” |
| 先小后大 | 8 例确认没崩 → 30 例看方向 → 全量只在里程碑跑 | 迭代期省 70%+ |

推荐节奏：

```bash
# 每次改 prompt / 解析逻辑
python -m evals.real_model_lab --profile smoke --write --out evals/out/smoke.json --report-path evals/out/smoke.md

# 准备合并前
python -m evals.real_model_lab --profile iterate --write --out evals/out/iterate.json --report-path evals/out/iterate.md

# 里程碑（发版、写简历、面试前）
python -m evals.real_model_lab --profile full --write
```

## 六、还能做但没做的

| 手段 | 为什么没做 |
| --- | --- |
| 响应缓存（同 brief + 同 prompt 直接复用） | 会抹掉采样方差，只适合开发期，不适合测量期；要区分两种模式才有意义 |
| 用更小的模型做初筛 | 需要先证明小模型与大模型的排序一致，否则是在测另一个东西 |
| 批量 API / 折扣时段 | 依赖供应商，且会改变延迟分布，属于部署优化而非评测优化 |
| 提示缓存（prompt caching） | 系统提示固定、可缓存，但当前中转站是否支持未知；输入只占 7% 成本，收益有限 |

## 七、一句话结论

**先压输出，再压轮数，最后才压输入。** 输出占九成；全量 3 轮的边际信息量远低于它的价格；输入已经是小头。
