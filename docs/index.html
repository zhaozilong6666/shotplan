shotplan

把一句模糊的「想去西安拍汉服」，变成能执行、能核对、能追溯的小时级方案。

核心不是调模型，而是让质量可被测量：生成前先判定需求是否可满足，生成后用一层不经过模型的硬约束校验器判定，并以带对照组的 60 个用例守住回归。 技术栈 Python / FastAPI / SQLite；核心引擎仅标准库，无 API key 也能完整跑通。

三件不交给模型的事

「AI 系统里哪些判断必须由确定性代码负责」，是这个项目最想回答的问题。

生成前

需求是否可满足

预算低于 350 元、时长短于 1.5 小时、城市不在知识库、必去与排除冲突时，直接返回原因、缺口、建议与理论下限，不生成硬凑方案。CLI 退出码 3，API 返回 status=infeasible。

生成后

方案是否可执行

时间不重叠、妆造先于拍摄、跨景点至少 20 分钟转场、预算不超、地点必须在白名单。12 条规则单一定义源，校验器、打分器、文档与 API 共用同一份定义。

评测

测量本身是否有效

同一批 brief 上同时跑规则 Agent 与故意犯错的对照组。若对照组均分追上正式方案，CI 判定「测量失效」并失败——先证明尺子是准的，再谈分数。

评测结果

60 个用例：normal 22、conflict 17、edge 12、infeasible 9。最后一组描述数学上无法满足的 brief，正确行为是结构化拒绝而非硬凑方案。

对照基线 naive：硬约束通过率 15.0%、均分 0.3115。差值 0.6647。 9 个 infeasible 用例因共享生成前判定而两组同分，区分度由其余 51 个用例提供——这一点在报告里如实写明。

修复循环：从「有这个功能」到「有数据」

三种刻意构造的 provider，在同一批 51 个可满足 brief 上跑「允许修复一轮」。每次接受/拒绝都读 trace 里的 accepted 字段，不靠推断。

有效

repairable

首轮 0% → 修复后 100%，一次修复成功率 51/51。说明校验报告作为修复提示是有效的。

无效

naive

忽略修复提示，51 次候选全部被拒绝，通过率不升。修复效果取决于 provider 是否真的使用报告。

被拦截

regressing

「越修越差」的 51 次候选全被单调保护拦下，均分不降。有修复循环不等于质量会变好。

成本与延迟（模拟，非实测）

失败案例库

357 条结构化记录，来自对照组的真实输出；每条包含输入 brief、输出片段、期望规则与修复建议。新增规则前先在这里找证据。

  • TRANSFER_BUFFER144 次 · 跨景点没留转场
  • UNKNOWN_LOCATION114 次 · 编造不存在的地点
  • BUDGET_EXCEEDED51 次 · 总花费超预算
  • TIME_OVERRUN48 次 · 时间轴超出预约时长

为什么值得看：每条规则都能追溯到一个真实失败，而不是拍脑袋加条款。接真实模型后，新错误按同样格式追加，再补规则与用例。
