shotplan

把一句模糊的「想去西安拍汉服」，变成能执行、能核对、能追溯的小时级方案。

核心不是调模型，而是让质量可被测量：生成前先判定需求是否可满足，生成后用一层不经过模型的硬约束校验器判定，并以带对照组的 80 个用例守住回归；再用 8 处受控变异验证门禁本身有效。 技术栈 Python / FastAPI / SQLite；核心引擎仅标准库，无 API key 也能完整跑通。

三件不交给模型的事

「AI 系统里哪些判断必须由确定性代码负责」，是这个项目最想回答的问题。

生成前

需求是否可满足

预算低于 350 元、时长短于 1.5 小时、城市不在知识库、必去与排除冲突时，直接返回原因、缺口、建议与理论下限，不生成硬凑方案。CLI 退出码 3，API 返回 status=infeasible。

生成后

方案是否可执行

时间不重叠、妆造先于拍摄、跨景点至少 20 分钟转场、预算不超、地点必须在白名单。12 条规则单一定义源，校验器、打分器、文档与 API 共用同一份定义。

评测

测量本身是否有效

同一批 brief 上同时跑规则 Agent 与故意犯错的对照组；对照组必须命中每一条已知硬规则。再注入 8 处受控故障，要求门禁全部拦截——先证明尺子是准的，再谈分数。

评测结果

80 个用例：normal 30、conflict 23、edge 16、infeasible 11。最后一组描述数学上无法满足的 brief，正确行为是结构化拒绝而非硬凑方案。

对照基线 naive：硬约束通过率 13.8%、均分 0.3014。差值 0.6774。 11 个 infeasible 用例因共享生成前判定而两组同分，区分度由其余 69 个用例提供——这一点在报告里如实写明。

门禁有效性：变异测试

80/80 全绿只能说明「当前代码通过了当前检查」。在进程内注入受控故障、跑同一套用例、要求真实门禁拒绝，再回滚逐字段比对——检验的是检查本身。完整实验报告 →

修复循环：从「有这个功能」到「有数据」

三种刻意构造的 provider，在同一批 69 个可满足 brief 上跑「允许修复一轮」。每次接受/拒绝都读 trace 里的 accepted 字段，不靠推断。

有效

repairable

首轮 0% → 修复后 100%，一次修复成功率 69/69。说明校验报告作为修复提示是有效的。

无效

naive

忽略修复提示，69 次候选全部被拒绝，通过率不升。修复效果取决于 provider 是否真的使用报告。

被拦截

regressing

「越修越差」的 69 次候选全被单调保护拦下，均分不降。有修复循环不等于质量会变好。
